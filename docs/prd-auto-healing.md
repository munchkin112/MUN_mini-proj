# Auto Healing 멀티 에이전트 프로젝트 PRD

## 1. 문서 정보

| 항목 | 내용 |
|---|---|
| 프로젝트 | AI 학습 퀴즈 생성기 Auto Healing |
| 버전 | 초안 0.1 |
| 작성일 | 2026-10-28 |
| 작성자 | Codex, 사용자와 협의 |
| 검토자 | 사용자 및 팀원 |
| 승인 상태 | 승인 대기 |
| 기간·팀 | 3일, 중급 개발자 4명 |

서비스와 사용자 입력은 확정된 내용이다. 재시도 대기시간 등 상세 정책의 수치는 3일 실습을 위한 **초안 제안값**이며 PRD 검토 시 조정할 수 있다.

## 2. 프로젝트 개요

학습자가 주제를 입력하면 객관식 문제 3개와 선택지, 정답, 해설을 제공한다. 문제 생성 의존 서비스의 장애를 탐지·진단하고 정해진 범위에서 복구한 뒤 독립적으로 검증한다. 복구 실패가 계속되면 자동 시도를 멈추고 운영자에게 알린다.

정상 문제 생성에는 사용자가 선택한 OpenAI GPT-4o mini API를 사용한다. 장애는 실제 외부 서비스가 아닌 로컬 모의 의존 서비스에서 재현한다. 같은 문제 생성 인터페이스를 통한 정상 경로와 모의 장애 경로는 명확하게 구분한다.

## 3. 문제 정의

문제 생성 API가 오류를 반환하거나 지연·연결 실패하면 학습자는 결과를 받지 못한다. 운영자는 실패를 확인하고 원인을 분류한 후 재시도와 정상화 확인을 수동으로 수행해야 한다. 제한 없는 재시도는 비용과 지연을 늘리고, 복구 성공을 확인하지 않으면 실제 장애가 남아 있어도 완료로 오인할 수 있다.

## 4. 사용자와 이해관계자

- **학습자:** 학습 주제를 입력하고 문제·정답·해설 또는 명확한 실패 안내를 받는다.
- **운영자:** 장애의 근거, 복구 이력, 독립 검증 결과와 수동 개입이 필요한 사건을 확인한다.
- **프로젝트 팀:** 4명의 중급 개발자. 3일 실습에서 기능과 장애 대응을 검증한다.

## 5. 목표와 성공 기준

1. 정상 요청에서 문제 3개를 반환하고 각 문제에 선택지, 정답, 해설을 제공한다.
2. 격리된 모의 의존 서비스에서 5xx, 타임아웃, 연결 실패를 각각 반복 재현하고, 사건별 탐지·진단·복구 시도·검증 또는 안전 중단의 근거를 기록한다.
3. 사건당 자동 복구 시도는 최초 사용자 요청 이후 최대 3회이며, 한도에 도달하면 자동 시도를 중단하고 운영자에게 알린다.
4. 독립 검증을 통과한 경우에만 정상 복구로 판정한다. 대체 문제 제공은 **대체 결과**로 표시하고 정상 복구로 집계하지 않는다.
5. 장애 주입·탐지·복구 시작·독립 검증 종료 시각을 남겨 사건별 탐지 및 정상화 시간을 계산한다.
6. 실제 API 사용을 월 20달러 예산 안에서 관리한다. 사용량·추정 비용 확인과 호출 중단 절차를 마련하며, 애플리케이션 추정치만으로 외부 계정 전체 청구액이 제한된다고 가정하지 않는다.

## 6. 비목표

회원가입·개인별 학습 이력·통계·맞춤 학습, 실제 개인정보 사용, 문제와 해설의 완전한 정답성 보장, 운영 환경에 대한 자동 변경, 임의 명령 실행, 실제 OpenAI 서비스에 대한 장애 주입은 범위에서 제외한다. RAG 구축과 대규모 문서 수집도 MVP 필수 범위가 아니다.

## 7. 정상 서비스 시나리오

1. 학습자가 가상의 학습 주제를 입력한다.
2. 퀴즈 생성 서비스가 주제를 문제 생성 의존 서비스에 전달한다.
3. 응답에 문제 3개, 각 문제의 선택지·정답·해설이 있는지 확인한다.
4. 조건을 충족하면 학습자에게 정상 결과를 보여주고 요청 결과를 기록한다.
5. 정상 모델 경로와 모의 장애 경로를 식별할 수 있어야 한다. 모의 결과를 실제 모델의 응답으로 표시하지 않는다.

형식 검증은 내용의 사실성을 보장하지 않는다. 데모에 사용하는 예시의 정답과 해설은 사람이 확인한다.

## 8. 장애 시나리오

모의 의존 서비스가 격리된 로컬 환경에서 다음 신호를 반환하도록 구성하는 것을 요구한다. 이 문서는 주입을 실행하지 않는다.

| ID | 장애와 신호 | 사용자 영향 | 안전한 재현 방향 |
|---|---|---|---|
| F-01 | 일시적 HTTP 5xx | 요청 실패 | 모의 서비스가 지정된 요청에 5xx 반환 |
| F-02 | 타임아웃 | 응답 지연·실패 | 모의 서비스가 허용시간을 넘겨 응답 |
| F-03 | 연결 실패 | 요청 실패 | 모의 의존 서비스 연결 실패 상태 제공 |
| F-04 | 동일 장애 반복 | 지속 실패·대기 | 모의 서비스가 복구 시도 상한을 넘겨 실패 |

## 9. 멀티 에이전트 구성

역할은 개념적 책임이며 모두 별도의 LLM 에이전트일 필요는 없다. 규칙이나 상태 전이로 충분한 부분은 단순하게 처리한다. 탐지·진단·복구·검증 책임은 구분한다.

| 역할 | 책임·입력 | 출력 | 허용 행동 | 금지 행동·실패 시 |
|---|---|---|---|---|
| Monitor | 상태·요청 결과를 관찰 | 사건과 신호 | 상태 조회, 사건 생성 | 설정 변경·복구 실행 금지; 관찰 불가 시 보고 |
| Diagnosis | 사건과 신호를 분류 | 장애 유형·근거·복구 제안 | 증거 조회와 정책 내 제안 | 직접 복구 금지; 원인 불명은 사람에게 전달 |
| Recovery | 정책에 맞는 조치를 수행 | 시도와 결과 | 지정된 요청 재시도 | 임의 명령·실제 서비스 재시작 금지; 상한 후 중단 |
| Verification | 복구 후 상태와 기능을 독립 확인 | 성공·실패와 근거 | 상태 확인과 지정된 검증 요청 | 자기 보고만으로 성공 판정 금지; 실패 시 중단·알림 |
| Orchestrator | 상태·순서·시도 상한 관리 | 다음 단계·최종 상태 | 역할 호출, 중단·알림 요청 | 권한·시도 제한 우회 금지; 불확실하면 안전 중단 |
| Notification | 운영자에게 사건 전달 | 알림·전달 결과 | 로컬 운영 화면 또는 로그에 알림 표시 | 정책 변경 금지; 전달 실패도 기록 |

## 10. 에이전트 협업 흐름

장애 신호 → 사건 생성 → 증거 기반 진단 → 허용된 복구 → 독립 검증 → 정상 복구 또는 실패. 원인 불명, 시도 상한, 검증 실패 등 정책에서 정한 중단 조건에서는 자동 시도를 멈추고 사람에게 알린다. 동일 사건의 상태와 시도 횟수는 모든 단계가 공유한다.

## 11. 장애별 복구정책

아래 시간은 실습용 초안 제안값이다. 복구 시도 최대 3회는 최초 사용자 요청을 제외한다. 각 재시도 전 대기시간은 1초, 2초, 4초로 제안하며 무작위 지연은 MVP 필수가 아니다.

| 장애 | 탐지·진단 근거 | 1차 복구 | 2차 복구 / 최대 시도 | 사람 승인 | 롤백·안전 중단 | 성공 검증 |
|---|---|---|---|---|---|---|
| 5xx | 5xx 응답 | 지정된 요청 재시도 | 최대 3회; 이후 알림 및 대체 문제 조건 검토 | 재시도 불필요 | 상한 후 중단 | 정상 응답과 퀴즈 형식 확인 |
| 타임아웃 | 제안값: 요청당 10초 초과 | 요청 종료 후 재시도 | 최대 3회; 이후 알림 | 재시도 불필요 | 기존 요청 결과가 늦게 와도 중복 완료 처리 방지 | 지정 시간 내 정상 응답과 형식 확인 |
| 연결 실패 | 연결 오류와 상태 확인 | 제한된 재시도 | 최대 3회; 이후 알림 | 재시도 불필요 | 임의 재시작 없이 중단 | 상태 확인과 실제 퀴즈 요청 확인 |
| 반복 실패 | 복구 시도 3회 실패 | 회로 차단·알림 | 자동 복구 중단 | 재개는 운영자 확인 | 차단 상태 유지 | 자동 호출이 중단되고 알림이 남았는지 확인 |

회로는 **사건에 대한 3회 복구 시도 실패 시** 열린다. 열린 동안 문제 생성 서비스로 새 자동 호출을 보내지 않는다. 운영자가 장애를 확인한 뒤 수동으로 회로 재개를 요청하면 한 번의 제한된 확인 요청을 허용하고, 독립 검증에 성공했을 때 정상 상태로 전환한다. 실패하면 다시 차단하고 알린다. 회로 범위는 해당 모의 의존 서비스의 로컬 실습 인스턴스로 제한한다.

사전에 준비한 대체 문제가 해당 주제에 존재하면 대체 결과임을 표시해 제공할 수 있다. 없으면 실패 안내를 반환한다. 어느 경우에도 이를 의존 서비스의 정상 복구로 기록하지 않는다.

## 12. 자율성과 Human-in-the-loop

- **자동 가능:** 모의 환경에서 상태 조회, 정책에 명시된 재시도, 회로 차단, 독립 검증, 대체 결과 표시, 운영자 알림.
- **사람 승인 후:** 차단된 회로 재개, 실습 설정 변경 또는 새 복구 행동 추가.
- **자동 실행 금지:** 임의 생성 명령, 허용되지 않은 서비스 재시작, 운영 데이터 삭제·수정, 인증정보 변경, 한도 없는 비용 발생 행동.
- **판단 불가:** 자동 변경을 수행하지 않고 근거와 함께 운영자에게 전달한다.

## 13. 기능 요구사항

### FR-001 퀴즈 생성
- 설명·입력: 학습 주제를 받아 문제 생성을 요청한다.
- 기대 동작: 문제 3개와 각 선택지·정답·해설을 반환한다.
- 예외: 빈 주제는 생성 호출 없이 오류를 안내한다.
- 인수조건: 정상 응답에서 문제 수와 각 필수 항목을 확인할 수 있다.

### FR-002 모의 장애 제공
- 설명·입력: 격리된 모의 의존 서비스에 장애 시나리오를 지정한다.
- 기대 동작: 5xx, 타임아웃, 연결 실패와 반복 실패를 각각 재현한다.
- 예외: 모의 경로를 실제 API 경로와 구별할 수 없으면 실습을 중단한다.
- 인수조건: 각 시나리오의 신호와 사건이 구분되며 실제 OpenAI 서비스에는 장애를 주입하지 않는다.

### FR-003 탐지와 사건 생성
- 설명·입력: 오류 응답, 시간 초과, 연결 실패 신호를 관찰한다.
- 기대 동작: 사건 식별자, 대상, 시각과 근거를 남긴다.
- 예외: 신호가 불충분하면 원인 미상으로 표시한다.
- 인수조건: 각 장애 후보에 대한 사건과 탐지 근거를 조회할 수 있다.

### FR-004 진단
- 설명·입력: 사건 및 관찰 근거를 바탕으로 장애를 분류한다.
- 기대 동작: 장애 유형과 허용된 복구 방향을 제시한다.
- 예외: 판단할 수 없으면 자동 변경 없이 운영자에게 전달한다.
- 인수조건: 분류 결과가 입력 근거와 연결되고 원인 미상 경로가 존재한다.

### FR-005 제한된 복구
- 설명·입력: 진단 결과와 정책을 받아 복구를 실행한다.
- 기대 동작: 최초 요청 이후 재시도는 사건당 최대 3회다.
- 예외: 상한 도달 또는 정책에 없는 조치는 실행하지 않는다.
- 인수조건: 시도별 결과가 기록되고 3회 실패 후 추가 자동 시도가 없다.

### FR-006 회로 차단과 재개
- 설명·입력: 연속 복구 실패와 운영자 재개 요청을 처리한다.
- 기대 동작: 3회 실패 시 차단하고, 운영자 재개 후 제한된 확인과 독립 검증을 수행한다.
- 예외: 재개 검증이 실패하면 다시 차단한다.
- 인수조건: 차단 중 자동 호출이 발생하지 않고 재개 성공·실패가 기록된다.

### FR-007 독립 검증
- 설명·입력: 복구 시도 결과와 검증 대상 서비스를 받는다.
- 기대 동작: 별도 단계가 상태 및 실제 퀴즈 응답의 필수 항목을 확인한다.
- 예외: 검증 불가·실패는 정상 복구가 아니다.
- 인수조건: 복구 단계의 성공 보고만으로 사건이 종료되지 않는다.

### FR-008 대체 결과와 알림
- 설명·입력: 복구 실패 사건과 준비된 대체 문제가 있는 주제를 받는다.
- 기대 동작: 대체 문제를 제공할 때 대체 결과임을 표시하고 운영자에게 알린다.
- 예외: 일치하는 대체 문제가 없으면 실패를 안내한다.
- 인수조건: 대체 결과, 정상 복구, 실패 상태가 구분되어 기록된다.

### FR-009 비용·추적 정보
- 설명·입력: 실제 API 요청의 사용량과 사건별 결과를 기록한다.
- 기대 동작: 사용량과 추정 비용, 호출 중단·재개 여부를 확인할 수 있다.
- 예외: 사용량이나 비용을 확인할 수 없으면 그 사실을 표시하고 운영자가 확인한다.
- 인수조건: 프로젝트에서 관측한 사용량과 계정의 실제 청구액을 구분한다. 20달러 예산은 전체 계정 사용량을 포함한 운영자 확인이 필요하다.

## 14. 비기능 요구사항

- **NFR-001 신뢰성:** 복구 시도 상한과 독립 검증을 지키며 중복 사건·결과를 식별한다.
- **NFR-002 안전성:** 모든 장애 주입과 복구 조치는 로컬 실습환경과 허용된 대상에 한정한다.
- **NFR-003 보안:** API 키를 문서, 결과 화면, 로그에 기록하지 않는다. 실제 개인정보를 입력하지 않는다.
- **NFR-004 관측 가능성:** 사건의 신호·판단·복구·검증·상태 변경을 식별자와 시각으로 연결한다.
- **NFR-005 재현성:** 최소 3개 장애를 동일한 모의 조건으로 반복할 수 있다.
- **NFR-006 성능:** 실습용 요청 타임아웃 초안은 10초. 실제 모델 응답 특성에 따라 검토하며 보장된 성능 목표로 간주하지 않는다.
- **NFR-007 설명 가능성:** 운영자가 판단 근거와 실행한 복구 정책을 확인할 수 있다.

## 15. 데이터와 로그 요구사항

사건 ID, 요청 추적 ID, 시나리오 유형, 장애 주입·탐지·복구 시작·각 시도·독립 검증 종료 시각, 관찰 신호, 진단 근거, 복구 행동과 결과, 회로 상태, 사람의 재개 요청, 대체 결과 여부, 최종 상태를 기록한다. 실제 API 사용량과 추정 비용은 확인 가능한 범위에서 기록한다. 시간은 타임존이 명시된 형식으로 기록한다. API 키, 인증정보, 실제 개인정보는 기록하지 않는다. 저장 위치와 보존 기간은 [미결정].

## 16. 검증 및 완료 기준

| 검증 대상 | 완료 기준 |
|---|---|
| 정상 흐름 | 실제 API가 사용 가능한 환경에서 요청이 문제 3개와 필수 항목을 반환한다. |
| 5xx·타임아웃·연결 실패 | 각 모의 장애의 탐지 신호, 사건, 정책에 따른 시도와 결과가 기록된다. |
| 독립 검증 | 복구 성공 보고만으로 완료되지 않으며, 정상 기능 확인 이후에만 정상 복구로 기록한다. |
| 반복 실패 | 최초 요청 이후 복구 시도가 3회를 넘지 않고 회로 차단과 운영자 알림이 기록된다. |
| 대체 응답 | 대체 결과 표시와 최종 상태가 정상 복구와 구별된다. |
| 시간·로그 | 주입·탐지·복구 시작·검증 종료 시각과 사건 식별자를 조회할 수 있다. |
| 비용 | 사용자가 프로젝트 사용량과 실제 계정 청구액을 구분해 확인하는 절차가 있다. |

사건별 탐지 시간은 탐지 시각−주입 시각이다. 사건별 정상화 시간은 **독립 검증이 성공한 시각−주입 시각**이다. MTTD·MTTR을 제시할 때는 집계한 사건 수와 실패·대체 결과의 처리 기준을 함께 기록한다. 대체 결과나 미복구 사건을 정상화 성공으로 집계하지 않는다.

## 17. 3일 MVP 포함·제외 범위

**포함:** 로컬 퀴즈 생성, 실제 GPT-4o mini API 경로, 모의 의존 서비스, 최소 3개 장애, 제한된 복구, 독립 검증, 회로 차단·사람 알림, 기본 추적과 사용량 확인.

**제외:** 회원·개인화 기능, 실제 개인정보, 대규모 데이터 수집·RAG, 실제 외부 서비스 장애 주입, 운영 인프라 자동 수정, 정답의 완전한 정확성 보장.

Python과 FastAPI는 팀의 경험 및 로컬 실행에 맞춘 후보이며, LangChain·LangGraph 사용 범위는 역할 분리의 필요성과 3일 범위에 맞춰 정한다. 실제 기술 선택은 필요할 때 검토한다.

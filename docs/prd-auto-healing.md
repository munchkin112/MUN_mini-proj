## 2. 프로젝트 개요

학습자가 주제를 입력하면 객관식 문제 3개와 해설을 받는다. 문제 생성 의존 서비스의 장애를 규칙으로 분류하고 장애별로 다른 허용된 복구 전략을 적용한다. 별도 검증이 정상화 여부를 확인하며, 실패가 계속되면 안전하게 중단하고 운영자에게 알린다.

정상 생성 경로는 사용자가 선택한 GPT-4o mini API다. 장애 실험과 자동 재시작의 대상은 격리된 로컬 모의 서비스다. 두 경로와 그 결과를 명시적으로 구분한다. 실행은 로컬을 기준으로 하며 강사가 지정한 Day 3 배포 환경은 **Docker 필수**다.

## 3. 문제 정의

생성 API의 서버 오류, 지연, 연결 실패 또는 응답 형식 오류는 학습자를 기다리게 하거나 잘못된 퀴즈를 보여줄 수 있다. 운영자는 어떤 장애인지 확인하고 다른 복구 조치를 선택한 뒤 실제 기능이 정상화됐는지 확인해야 한다. 모든 실패에 같은 재시도를 적용하면 대기와 비용이 늘고, 대체 응답을 복구 성공으로 착각할 수 있다.

## 4. 사용자와 이해관계자

- 학습자: 학습 주제를 입력하고 유효한 퀴즈, 표시된 대체 결과 또는 실패 안내를 받는다.
- 운영자: 로컬 사건 조회 API에서 사건과 차단 상태를 확인하고 허용된 수동 재개를 요청한다.
- 팀·강사: 4명 팀이 3일 실습을 진행하고 강사가 Docker 환경의 시연을 확인한다.

## 6. 비목표

회원가입, 개인화·학습 이력, 실제 개인정보, 대규모 RAG·문서 수집, 실제 OpenAI 장애 주입, 운영 인프라 재시작, 임의 명령 실행, 답변 내용의 완전한 정확성 보장은 제외한다. Docker 구성과 테스트의 **실제 작성·실행은 이후 단계**에 해당한다.

## 7. 정상 서비스 시나리오

학습자가 주제를 입력하면 서비스는 요청 ID와 접수 상태를 즉시 반환한다. 간단한 로컬 클라이언트는 조회 API를 잠정 1초 간격으로 확인해 상태와 결과를 표시한다. 대체 결과가 6초에 준비되면 다음 조회 시 표시되며 통신·표시 지연은 별도다. 백그라운드 생성이 끝나면 검증된 문제를 반환한다. 문제 수는 정확히 3개, 문제당 선택지는 A·B·C·D 네 개이며 공백이 아닌 서로 다른 문자열이다. 정답은 선택지에 존재하는 문자 하나, 문제와 해설은 공백이 아닌 한국어다. 자동 형식 검사는 문제와 해설에 한글 음절이 적어도 하나 있는지 확인하며 언어의 자연스러움·사실성은 보증하지 않는다. 데모의 정답과 해설은 사람이 검토한다.

## 8. 장애 시나리오

| ID | 장애 | 신호·격리된 재현 | 기본 전략 |
|---|---|---|---|
| F-01 | 일시적 5xx | 모의 생성 경로가 5xx 반환 | 제한된 백오프 재시도 |
| F-02 | 타임아웃 | 모의 생성 경로가 잠정 6초 이내에 응답하지 않음 | 대체 문제를 먼저 제시하고 남은 시간에 제한적 복구 |
| F-03 | 연결 실패 | 허용된 로컬 모의 서비스 연결 불가 | 대상 확인 후 모의 서비스 재시작, 헬스체크 대기 |
| F-04 | 응답 형식 오류 | 문제 수·선택지·정답 등 형식 조건 위반 | 새 생성 요청으로 제한적 재생성 |
| F-05 | HTTP 429 | 모의 또는 실제 경로의 한도 초과 응답 | 분류·기록 후 자동 재시도 중지, 운영자에게 안내 |

**반복 실패·재시도 소진은 장애 유형이 아니라 F-01~F-04의 진행 결과**다. 429의 재현은 Should이며 실제 API에 한도 초과를 강제로 일으키지 않는다.

## 9. 역할과 구현 방식

LangGraph 상태기계가 사건 상태, 남은 시간, 시도 횟수와 회로 상태를 조정한다. Monitor·Diagnosis·Recovery·Verification은 결정적 규칙과 코드로 정의하며, 각 역할을 별도 LLM으로 만들지 않는다. 퀴즈 생성에만 GPT-4o mini를 사용한다. 원인 불명 사건의 LLM 보고문은 Should이며 예산·시간 범위 안에서만 사용한다. 보고문은 복구 결정에 권한이 없다.

| 역할 | 입력 → 출력 | 허용 | 금지·실패 시 |
|---|---|---|---|
| Monitor | 요청 결과·모의 헬스 프로브 → 사건과 시각 | 관찰, 사건 생성 | 변경·복구 금지; 관찰 실패 기록 |
| Diagnosis | 상태 코드·예외·형식 결과 → 분류와 근거 | 규칙 분류, 허용 정책 선택 | 직접 조작 금지; 미분류는 중단·알림 |
| Recovery | 사건·정책 → 시도 결과 | 제한된 재시도·재생성·허용목록의 로컬 모의 서비스 재시작 | 허용목록 밖 재시작·임의 명령 금지; 실패 시 중단 |
| Verification | 사건·대상 → 독립 검증 결과 | 새로운 모의 헬스 및 생성 확인 요청, 결정적 형식 검사 | 복구의 응답 재사용·자기 보고만으로 성공 판정 금지 |
| Orchestrator | 사건·시간·시도·회로 → 상태 전이 | 정책에 맞춘 호출·중단 | 상한과 권한 우회 금지 |
| Notification | 사건·최종 상태 → 운영자 알림 | 로컬 조회 API 및 로그에 기록 | 복구 정책 변경 금지 |

## 10. 사용자 및 협업 흐름

사용자 요청 → 요청 ID·접수 상태 반환 → 생성 요청 → 신호 관찰·분류 → 전략 실행 → 독립 검증 → 정상 복구 또는 안전 중단. 조회 API로 `PROCESSING`, `COMPLETED`, `DEGRADED`, `FAILED`를 확인한다. 타임아웃 발생 시 준비된 주제의 대체 문제가 있으면 `DEGRADED`와 함께 즉시 조회 가능하게 하고 사용자 결과는 고정한다. 클라이언트는 다음 조회 시 대체 결과를 표시한다. 뒤늦은 응답이 대체 결과를 덮어쓰지 않는다. 서비스 복구·운영자 기록은 별도로 전체 제한시간까지 계속될 수 있다. 준비된 문제가 없으면 처리 중 상태를 유지하고 종료 시 실패를 반환한다.

## 11. 장애별 복구정책과 통제

최초 사용자 생성 요청은 복구 횟수에 포함하지 않는다. 각 사건의 복구 행동은 최대 3회이며, 재시도·재생성·재시작 각각 1회로 계산한다. **요청 단위 복구 상한**과 **서비스 단위 회로**는 별도로 관리한다.

| 장애 | 탐지·진단 | 1차 전략 | 2차·상한 | 승인 / 롤백·안전 중단 | 독립 성공 검증 |
|---|---|---|---|---|---|
| 5xx | 5xx 상태 | 동일 요청 재시도 | 최초 요청 후 최대 3회, 잠정 대기 0.5·1·2초 | 자동 허용; 시간·횟수 소진 시 중단·알림 | 새 모의 생성 요청과 결정적 형식 검사 |
| 타임아웃 | 요청당 잠정 6초 초과 | 일치하는 대체 문제 즉시 제시 | 남은 시간 내 최대 3회 재시도 | 대체 결과 유지; 늦은 응답 무시, 소진 시 알림 | 별도 모의 생성 요청; 대체 표시만으로 복구 성공 불가 |
| 연결 실패 | 연결 예외와 모의 서비스 상태 | 허용목록 대상의 로컬 모의 서비스만 1회 재시작 | 잠정 4초 안에 독립 헬스 확인, 실패 시 중단·알림 | 승인된 로컬 대상만 자동; 재시작 취소 불가이므로 실패 시 안전 중단 | 새 헬스 및 새 모의 생성 요청 |
| 형식 오류 | 문제 수·선택지·정답·해설 검사 실패 | 새로운 생성 요청으로 재생성 | 최대 2회 재생성; 재발 시 중단·알림 | 자동 허용; 유효하지 않은 응답 폐기 | 새 모의 생성 요청을 별도 검사 |
| 429 | HTTP 429·가능한 재시도 지시 정보 | 한도 초과로 분류, 현재 사건의 즉시 자동 재시도 중지 | 운영자에게 남은 제한시간·근거 전달 | 무작위 재시도 금지; 대체 문제는 별도 표시 | 사람의 한도 확인 후 별도 요청; 자동 복구 성공으로 집계하지 않음 |

재생성 2회는 잘못된 출력을 반복하는 비용을 제한하기 위한 잠정값이며 사건 상한 3회보다 작다. 모의 서비스 재시작은 최대 1회로 범위를 제한한다. 라우팅을 미리 승인된 대체 문제 경로로 전환한다면 변경 전 경로를 보존하고 복귀 검증이 실패할 때 직전 경로를 복원한다. 대체 문제는 외부 API의 복구가 아니라 저하 상태의 사용자 결과다.

| 사용자 상태 조회 | 잠정 1초 간격 | 로컬 클라이언트에서 빠른 상태 확인을 보여주기 위한 가정이며 실측 후 조정한다. |

| 재시작 헬스 대기 | 최대 4초 | 6초 검증 예비 시간 내 연결 복구 여부를 빠르게 판정하기 위한 가정. 로컬 실측 후 조정한다. |
| 형식 오류 재생성 | 최대 2회 | 이미 두 번 형식이 어긋날 때 추가 비용을 제한하기 위한 임시값. 형식 오류율 실측 후 조정한다. |
| 모의 프로브 | 2초 간격 | 연속 상태 관찰과 실험 시간을 균형 있게 잡기 위한 가정. 모의 환경 탐지 지연을 보고 조정한다. |
| 회로 차단 | 30초 관찰창에 서비스 호출 연속 5회 실패 | 단일 사건 실패와 별도로 서비스 수준의 반복 장애를 판단하기 위한 가정. 실험 후 조정한다. |
| 반복 실험 | 장애별 5회 | 4회 정상화와 1회 지속 실패를 포함해 성공과 중단 경로를 모두 보여주기 위한 최소 데모 표본. 통계적 신뢰성을 주장하지 않는다. |

이전 동기 방식의 최악 대기 47초(10+1+10+2+10+4+10)는 더 이상 사용자 요청을 붙잡지 않는다. 비동기 접수 후 위 시간과 남은 예산을 적용한다. 잠정 수치가 동시에 모든 재시도를 완료한다고 가정하지 않는다. 남은 시간이 부족하면 시도 횟수가 남아 있어도 새 시도를 시작하지 않는다. 30초 도달 시 진행 중 호출을 취소 요청하거나 결과를 무시하고 미검증 사건을 종료·알림한다. 취소 요청이 공급자의 과금 중단을 보장하지는 않는다.

### 서비스 단위 회로 차단

회로는 **경로별 의존 서비스 인스턴스** 단위다. 동일 인스턴스에 대한 생성 호출의 5xx·타임아웃·연결 실패가 관찰창 30초 안에서 연속 5회 발생하면 열린다. 서로 다른 사건의 실패도 포함하며 정상 생성 호출 1회가 연속 카운터를 초기화한다. 30초가 지나면 창 밖의 실패는 제외한다. 형식 오류·429·프로브 실패는 이 호출 실패 카운터에 포함하지 않는다. 사건별 3회 한도 소진만으로 회로를 자동 개방하지는 않는다. 열린 회로는 해당 인스턴스의 신규 자동 생성 호출을 막고 사건을 기록한다. 운영자가 로컬 조회 API로 재개를 요청하면 반개방 상태에서 **한 번의 독립 확인 요청**을 허용하고 검증 성공 시 닫는다. 실패 또는 타임아웃이면 다시 연다. 재개 흐름은 Should이며 미구현 시 열린 상태 유지와 운영자 안내가 Must다.

## 12. 자율성과 Human-in-the-loop

- 자동: 정책 내 재시도·재생성, 허용목록에 등록된 로컬 모의 서비스의 최대 1회 재시작, 헬스 확인, 회로 차단, 대체 경로 전환·복귀, 독립 검증 및 알림.
- 사람 승인: 열린 회로의 수동 재개, 허용목록·실습 설정 변경, 새 복구 행동 추가, 실제 API를 사용하는 추가 검증 요청.
- 금지: 허용목록 밖 서비스 재시작, 실제 외부·운영 서비스 재시작, 임의 생성 명령, 운영 데이터·인증정보 변경, 비용 무제한 호출.
- 판단 불가·복구 실패: 자동 변경 중단, 증거·상태 기록, 운영자 알림.

## 13. 기능 요구사항과 우선순위

Must는 승인된 MVP의 완료 조건이다. Should는 시간이 허용할 때 추가하며 미구현 시 명시된 대체 행동을 사용한다.

### FR-001 퀴즈 생성·접수 — Must
- 입력: 주제. 동작: 비동기 요청 ID·상태를 반환하고 로컬 클라이언트가 조회하며, 문제 3개, A–D 선택지 4개, A–D 정답 한 개, 한국어 문제와 해설을 제공한다.
- 예외: 빈 주제는 생성 호출 없이 오류. 인수조건: 7절의 결정적 형식 검사를 통과한 결과만 정상 완료한다.

### FR-002 모의 장애 — Must
- 입력: 로컬 격리 시나리오. 동작: F-01~F-04를 재현하고 실제 API 경로와 표시를 구분한다. F-05 재현은 Should다.
- 예외: 모의 대상 확인이 안 되면 주입을 중지한다. 인수조건: 네 신호를 반복 생성하고 실제 외부 서비스는 변경하지 않는다.

### FR-003 탐지·진단 — Must
- 입력: 요청 결과와 로컬 모의 헬스 신호. 동작: 사건 ID, 탐지 시각, 근거와 네 장애 및 429를 규칙으로 분류한다.
- 예외: 원인 미상은 자동 변경 없이 알림. 인수조건: 429는 원인 미상이 아니며 즉시 자동 재시도하지 않는다.

### FR-004 장애별 복구 — Must
- 입력: 분류·정책·남은 시간. 동작: 11절의 재시도, 대체 경로, 허용목록 로컬 재시작, 재생성을 구분한다.
- 예외: 상한·권한·시간 위반 시 중단. 인수조건: 각 행동의 대상과 횟수 기록, 로컬 모의 대상 외 재시작 없음.

### FR-005 회로 차단 — Must; 수동 재개 — Should
- 입력: 인스턴스별 생성 호출 결과. 동작: 11절의 서비스 수준 연속 실패 기준으로 회로를 열고 신규 자동 호출을 막는다.
- 예외: 수동 재개 미구현 또는 실패 시 열린 상태 유지·알림. 인수조건: 단일 사건 소진만으로 열지 않으며 다른 사건을 포함한 연속 실패로 연다.

### FR-006 독립 검증 — Must
- 입력: 복구 대상과 검증 기준. 동작: Recovery 응답을 재사용하지 않고 Verification이 모의 경로로 새로운 헬스 및 고정 가상 주제의 새 생성 확인을 요청하고 형식을 결정적으로 검사한다.
- 예외: 검증 실패·시간 초과는 미복구. 인수조건: 별도 요청 ID와 검사 결과가 남는다. 모의 확인에는 실제 API 비용이 없으며 실제 API의 새 생성 검증은 운영자 승인 후 수행하고 호출 한도에 포함한다.

### FR-007 대체 결과·알림 — Must
- 입력: 타임아웃·준비된 대체 문제. 동작: 잠정 6초에 주제가 일치하면 대체 표시된 결과를 조회할 수 있게 하고 운영자에게 기록한다.
- 예외: 대체 문제가 없으면 처리 중 후 실패. 인수조건: `DEGRADED`와 정상 복구를 구별하고 늦은 응답이 결과를 덮어쓰지 않는다. 대체 경로에서 기존 경로로의 자동 복귀는 Should다.

### FR-008 상태·운영자 조회 — Must
- 입력: 사용자 요청 ID 또는 운영자 사건 ID. 동작: 로컬 조회 API로 사용자 상태, 운영자 사건·회로·시도 이력을 조회한다.
- 예외: 모르는 ID는 명확한 오류. 인수조건: 정상·대체·실패 및 차단 여부가 구분된다. 수동 재개 API는 Should다.

### FR-009 호출 한도·사용량 — Must; 자동 비용 추정 — Should
- 입력: 실제 API 요청·반환 사용량. 동작: 실습 실행당 실제 호출 최대 100회, 입력·출력 토큰 및 반환되지 않은 사용량을 기록한다. 운영자가 한도를 확인·재설정한다.
- 예외: 한도 도달 시 실제 API 자동 호출을 중단하고 알린다. 인수조건: 재시도와 실제 독립 검증 호출도 상한에 포함하며 계정 전체 청구액과 로컬 집계를 혼동하지 않는다.

## 14. 비기능 요구사항과 우선순위

- **NFR-001 신뢰성 / Must:** 사건별 시도 및 30초 전체 제한과 서비스별 회로 규칙을 지킨다.
- **NFR-002 안전성 / Must:** 모의 환경만 장애 주입하고 허용목록 로컬 모의 서비스만 자동 재시작한다.
- **NFR-003 저장소·비밀정보 / Must:** API 키·실제 개인정보를 문서, 화면, 로그에 남기지 않는다. 구현 단계에 `.env`와 로그 폴더를 `.gitignore`로 제외하고 커밋 전 시크릿 점검을 요구한다. 실제 비밀정보가 이미 추적됐다면 삭제만으로 안전하다고 가정하지 않고 별도로 대응한다.
- **NFR-004 관측 가능성 / Must:** 사건 ID·요청 ID·근거·조치·검증·차단·알림과 시각을 연결한다.
- **NFR-005 재현성 / Must:** 네 모의 장애를 격리 환경에서 각각 5회 반복하고 결과를 기록한다.
- **NFR-006 사용자 대기 / Must:** 비동기 접수와 30초 백그라운드 상한을 적용한다. 잠정 수치는 실측 후 확정한다.
- **NFR-007 설명 가능성 / Must:** 규칙에 따른 진단과 조치 근거를 로컬 조회 API로 확인한다. LLM 보고문은 Should다.

## 15. 데이터와 로그 요구사항

사건 ID, 사용자·검증 요청 ID, 대상 인스턴스, 실제·모의 경로, 장애 유형, 주입·탐지·복구 시작·각 시도·검증 종료 시각, 근거, 조치 대상과 횟수, 회로 전이, 사람 요청, 대체 여부, 최종 상태와 실제 API 토큰 사용량을 기록한다. 시간은 시간대가 포함된 형식으로 남긴다. 키·개인정보와 전체 입력 원문은 기록하지 않는다. 로그 위치·보존 기간은 O-03에서 정한다.

## 16. 검증, 지표 및 목표 추적

### 관찰과 시간 정의

Monitor는 모의 서비스에 잠정 **2초 간격의 경량 헬스 프로브**를 보내고 사용자 생성 요청의 오류·타임아웃·형식 오류도 관찰한다. 모의 프로브는 실제 LLM 호출이 아니다. 실험 시작 시 모의 장애 상태를 설정해 `injected_at`을 남기고, 다음 프로브 또는 요청에서 **해당 장애를 판별하는 신호**를 최초로 관찰했을 때 `detected_at`을 남긴다. 헬스만으로 5xx·형식 오류를 판별할 수 없는 경우에는 지정된 모의 기능 확인 요청에서 해당 신호를 관찰한다. 탐지 지연에는 프로브 간격뿐 아니라 기능 요청을 기다린 시간이 포함된다. 실험별 기능 요청 시점과 신호 경로를 기록하고 능동 탐지와 요청 관찰 결과를 혼합해 하나의 SLA로 주장하지 않는다.

| 지표 | 정의·판정 규칙 |
|---|---|
| 사건별 탐지시간 | `detected_at - injected_at`; 미탐지 건은 평균에서 제외하되 미탐지 수와 관찰 종료시간을 함께 보고한다. |
| MTTD | 탐지된 사건의 탐지시간 합 / 탐지된 사건 수. 시나리오별·신호 경로별로 표시한다. |
| 사건별 정상화시간 | 독립 검증 성공 시각 − 주입 시각. 대체·실패·미검증은 정상화로 간주하지 않는다. |
| MTTR | 독립 검증에 성공한 사건의 정상화시간 합 / 성공 사건 수. 성공 건수·전체 건수와 미복구 건수를 함께 표시한다. |
| 자동 복구 성공률 | 독립 검증으로 정상 복구한 사건 수 / 해당 시나리오의 전체 주입 사건 수. |
| 에스컬레이션율 | 운영자 개입이 필요해 알림으로 전환된 사건 수 / 전체 주입 사건 수. 대체 결과만으로 반드시 에스컬레이션했다고 가정하지 않는다. |
| 형식 검사 | 정확히 3문제, 각 4개 비어 있지 않고 서로 다른 선택지, A–D에 속하는 정답 1개, 문제·해설에 한글 음절과 공백 아닌 내용이 있는지 판정한다. |

각 F-01~F-04에서 5회씩 총 20회: **4회는 복구 가능한 모의 조건, 1회는 지속 실패 조건**으로 정한다. 반복 조건, 주입 시각과 기능 요청 시점을 고정해 기록하고 독립 검증 전 장애 상태의 해제 여부를 명시한다. 연결 실패는 재시작으로 모의 상태가 회복되도록 하며 지속 실패 1회는 재시작 후에도 실패하도록 구성한다. 예상 결과는 각 복구 가능 4건의 독립 검증 성공과 지속 실패 1건의 안전 중단·알림이다. 회로는 별도의 연속 실패 확인에서 두 사건 이상에 걸쳐 같은 인스턴스의 5번째 실패로 열리는지 확인한다. 이것은 계획된 데모 판정이며 아직 실측·실행 결과가 아니다. F-05는 별도 Should 분류 확인이다. 모의 경로의 검증 성공은 실제 API의 정상화 증거가 아니다. 실제 API 장애를 겪은 사건은 운영자가 승인한 실제 경로의 별도 확인이 성공할 때에만 실제 경로 정상 복구로 기록한다.

| 목표 | 요구사항 | 검증 증거 |
|---|---|---|
| G1 | FR-001, FR-006 | 형식 검사 결과와 사용자 상태 |
| G2 | FR-002~004, FR-006 | 장애별 사건·전략·독립 요청 이력 |
| G3 | FR-001, FR-007, FR-008, NFR-006 | 접수·대체·종료 시각 및 결과 상태 |
| G4 | FR-004~006, NFR-001~002 | 복구 횟수, 재시작 대상, 회로·검증 로그 |
| G5 | FR-002~003, NFR-004~005 | 시나리오별 5회 기록과 지표 산출 |
| G6 | FR-009, NFR-003 | 호출 수·토큰 기록과 Docker 실행 결과 |

## 17. 3일 MVP 범위와 배포

Must: 비동기 퀴즈 생성, 실제 API 정상 경로와 모의 장애 경로, 네 장애 분류·차별화된 복구, 안전 중단·알림·독립 검증, 서비스 단위 회로 차단, 운영자 조회 API, 호출 상한·토큰 로그, Docker 환경 최종 시연. Should: 429 모의 재현, 운영자 수동 회로 재개, 대체 경로 자동 복귀, 원인 불명 LLM 보고문, 자동 비용 추정. Should가 빠져도 회로는 안전하게 열린 상태로 유지하고 사람에게 안내한다. 배포 형태는 **강사 지정 Docker 필수**로 확인됐다. Docker 산출물의 세부 방식은 다음 단계에서 정한다.

## 18. 비용·위험과 대응

GPT-4o mini 표준 텍스트 요금의 확인값은 입력 100만 토큰당 **$0.15**, 출력 100만 토큰당 **$0.60**이다. [OpenAI 모델 요금](https://developers.openai.com/api/docs/models/gpt-4o-mini) (2026-10-28 확인). 가격과 모델 접근성은 변경될 수 있다.

가정상 입력 1,000·출력 800토큰이면 호출당 `1000/1,000,000×0.15 + 800/1,000,000×0.60 = $0.00063`이다. 최초 1회와 복구 3회를 모두 유료로 호출하면 사건당 최대 가정 비용은 $0.00252. 네 장애 × 5회 × 4회 = 80회가 모두 같은 토큰량의 유료 호출이라는 **가상 상한 예시**는 $0.0504로 $20의 약 0.252%다. 실제 20회 장애 실험은 모의 서비스로 수행하므로 이 80회를 실제 API에 요청하지 않는다. 토큰량, 불완전 응답, 과금 방식, 별도 도구 및 실제 검증 호출에 따라 비용은 달라진다. 실습당 실제 호출 100회 상한은 프로젝트에서 관리하는 안전 장치이며 동일 토큰 가정 시 $0.063이다. 실제 계정 전체 지출 상한은 별도 확인이 필요하다.

모델명은 설정값으로 두고 시연 전 [OpenAI 종료 일정](https://developers.openai.com/api/docs/deprecations)을 확인한다. 공식 문서는 `gpt-4o-mini-2024-07-18`의 종료 예정일을 2027-01-14로 기재한다. 형식 검증은 내용 정확성을 보장하지 않으며 사람이 데모 결과를 확인한다. 모의 실험 결과를 실제 외부 장애 복구 성과로 일반화하지 않는다.

### Gate 4 자체 검토 결과

**충족:** 서비스·사용자·정상 결과, 네 모의 장애, 429 분류, 역할·권한, 전략별 복구, 독립 검증, 자동·승인·금지 행동, 시도·회로·전체 시간 제한, 지표·5회 반복 계획, Docker 요구사항, Must/Should와 목표 추적을 명시했다.

**보완:** 실측 전 정책 수치는 잠정이며, 계정 접근·실제 청구 한도·로그 보존과 Docker 시연 세부 조건은 19절에 남았다. 5회 표본은 통계적 신뢰성을 제공하지 않는다. 실제 API 비용과 장애별 시연은 아직 측정하거나 실행하지 않았다.

**범위 초과 위험:** 실제 API와 모의 경로, 비동기 상태, 네 전략, 서비스별 회로와 Docker를 3일에 모두 다뤄야 한다. Should를 제외하고도 시간이 부족하면 사용자와 Must 범위를 재협의한다.

**승인 권고:** 수정 후 검토. 사용자·팀이 잠정 정책과 미결정 사항을 확인한 뒤 승인 여부를 결정한다.

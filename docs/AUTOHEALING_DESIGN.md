# 한강버스 전통시장 연계 자동 복구 상세 설계

> 보관 문서  현재 범위와 구현 및 장애 시험과 제출 기록의 기준은 [PRD](PRD.md)
> 이 문서는 이전 설계 이력이며 추가 요구사항 관리와 결과 기록은 PRD에서만 수행


문서 상태  구현을 위한 설계이며 실제 복구 성공과 장애 시험 결과는 아직 없음  
범위  선택한 한강버스 배편과 도착지 주변 전통시장 먹거리 코스  
별도 관광 코스는 MVP(첫 버전)에서 제외  
기준  [PRD](PRD.md)  [구현 명세](IMPLEMENTATION_SPEC.md)

## 1 어디에 넣는가

FastAPI(서버 프레임워크)의 요청 처리 계층에 Supervisor와 Recovery를 배치  
React(화면)는 백엔드가 반환한 상태를 표시하며 자동 재요청을 겹쳐 실행하지 않음  
Supervisor는 규칙으로 작업 순서와 재시도 및 최종 종료를 관리  
Planner와 Executor 및 Critic은 각각 분리된 에이전트 역할로 구현하고 도구 권한과 입출력을 분리  
Critic은 Python 검증 도구로 장소와 서버 계산값 및 출처를 비교하고 판정 이유를 전달  
Recovery는 Python 복구 모듈이며 다섯 번째 에이전트라고 계산하지 않음  
컨테이너 재시작이나 EC2 재부팅은 이번 자동 복구 범위에 포함하지 않음

정상 요청  화면 → Supervisor → Executor 자료 조회 및 서버 계산 → Planner 시장 코스 생성 → Critic 검증 → Supervisor 응답  
실패 요청  해당 단계 감지 → Supervisor 예산 확인 → Recovery 지정 동작 → 실패 단계 재실행 → 서버 검증 및 Critic → Supervisor 종료  
자료 갱신  관리자 실행 → 같은 Supervisor와 Recovery 정책 적용 → 외부 자료 조회 → 검증 → 새 버전 저장 → 재조회 검증

## 2 사용자의 실제 흐름과 실패 표시

| 시점 | 하는 일 | 성공 결과 | 끝내 실패할 때 화면 |
|---|---|---|---|
| 조건 선택 | 날짜와 출발 및 도착 선착장과 시간 및 예산 선택 | 지원 조건으로 검색 | 입력 오류는 해당 항목 수정 요청 |
| 배편 검색 | Executor가 저장된 운항표를 조회하고 서버가 시각과 요금을 계산 | 확인된 배편 목록과 출처 및 적용일과 확인 시각 | DB 장애는 배편 조회 불가  정상 빈 결과는 해당 배편 없음 |
| 배편 선택 | 배편 식별값과 자료 개정 번호를 서버가 다시 대조 | 선택 배편의 도착 예정 시각과 요금 | 만료나 개정으로 달라졌으면 최신 목록에서 다시 선택 |
| 시장 자료 조회 | 도착지와 연결된 저장 시장 및 업소와 메뉴 및 이동 근거 조회 | 확인된 후보와 가격 및 운영정보 | 배편 정보는 유지하고 시장 정보 조회 불가 |
| 시장 코스 생성 | Planner가 후보 식별값과 방문 순서 및 이유를 반환 | 검증 대기 코스 | 배편 정보는 유지하고 시장 코스 추천 이용 불가 |
| 결과 검증 | Critic과 서버 검증 도구가 원천과 계산값 대조 | 검증된 코스와 항목별 확인 상태 | 불완전 코스는 숨기고 배편 정보는 유지 |

배편 정보 유지도 그 배편 자료의 권한과 적용기간 및 유효성이 유지되는 동안만 허용  
시장 코스 실패 뒤 새로 배편을 만들거나 검증하지 않은 고정 코스로 대체하지 않음  
미확인 가격은 0원으로 계산하지 않고 예산 확인 필요 표시  
가격이나 영업정보의 정상적인 누락은 시스템 고장이 아니므로 재시도하지 않음

## 3 공통 제한과 최종 결정

| 설정 | 기준 |
|---|---|
| 외부 자료 조회 제한 | 시도당 10초  제한을 넘으면 해당 작업 취소 |
| 에이전트와 LLM 응답 제한 | 시도당 10초 |
| DB 연결과 개별 조회 제한 | 시도당 3초 |
| 일시 오류 재시도 | 실패 단계 최초 1회와 재시도 1회로 총 2회 실행 |
| 재시도 대기 | 1초  남은 전체 시간 안에서만 대기 |
| 전체 요청과 갱신 작업 제한 | 각각 시작부터 40초  재시도해도 초기화하지 않음 |
| Planner 재실행 예산 | 예외와 형식 오류 및 품질 반려를 합쳐 추가 실행 최대 1회 |
| 전체 LLM 호출 한도 | 요청당 최대 6회  단계별 한도와 전체 기한이 먼저 우선 |

에이전트 내부 SDK와 DB 드라이버 및 HTTP 도구의 숨은 자동 재시도는 끄거나 이 예산에 통합  
Critic 재검증 실패가 Planner 수정 예산을 새로 만들지 않음  
남은 시간으로 다음 시도를 수행할 수 없으면 재시도 없이 DEADLINE_EXCEEDED 종료  
늦게 도착한 결과는 응답에 반영하지 않음  
Supervisor가 SUCCESS와 PARTIAL 및 FAILED와 NEEDS_CONFIRMATION 중 최종 상태를 결정  
PARTIAL은 검증된 배편만 제공하고 시장 코스는 실패했음을 뜻하며 전체 코스 자동 복구 성공으로 집계하지 않음

## 4 FT-01 자료 갱신 중 외부 API 시간 초과

시점  사용자가 배편 검색할 때가 아니라 관리자가 운항표나 시장 자료 갱신을 실행할 때  
사용 전제  실제 외부 API의 사용과 저장 권한 및 필요한 필드를 확인한 경우만 연결  
공식 API가 없으면 허용된 파일 반영으로 운영하고 모의 API 시험을 실제 연동 성공으로 기록하지 않음

1  Supervisor가 refresh_job_id와 source_id 및 시작 시각을 부여
2  외부 자료 어댑터가 요청하고 10초 초과 시 작업을 취소한 뒤 SOURCE_TIMEOUT 반환
3  Recovery가 Supervisor 승인 후 1초 기다려 같은 자료를 한 번 재조회
4  응답이 오면 형식과 필수 필드 및 적용기간과 권한을 검사
5  새 개정 자료를 트랜잭션으로 저장하고 필요한 배편을 다시 조회해 저장 성공 확인
6  두 번째도 실패하면 새 버전 저장을 중단하고 이전 버전을 그대로 유지
7  이전 버전은 저장 권한과 expires_at 및 여행 날짜의 적용기간이 모두 유효할 때만 계속 제공
8  이전 자료가 만료됐거나 유효성 미확인이면 확인 필요 표시와 함께 해당 배편 선택 차단
9  관리 작업에는 갱신 실패와 이전 자료 제공 여부를 별도로 기록하고 담당자 알림

정상 API 재응답과 검증 성공은 RECOVERED  
유효한 이전 자료 제공은 FALLBACK_VALID이며 자료 갱신 성공과 구분  
HTTP 401과 403 및 잘못된 키는 재시도하지 않고 설정 확인 알림  
429는 Retry-After가 남은 기한 안일 때만 한 번 재시도  
원천이 정상적으로 빈 목록을 반환한 경우 통신 장애로 만들지 않음  
새 원천 응답을 받은 시각과 마지막 성공 갱신 시각 및 사용자에게 제공한 버전의 확인 시각을 따로 기록

## 5 FT-02 시장 코스 단계의 에이전트 예외

시점  Executor 자료 도구 선택 또는 Planner 코스 생성 또는 Critic 검증 실행 중  
감지  실행 래퍼가 예외와 10초 초과를 잡아 AGENT_EXCEPTION 또는 AGENT_TIMEOUT 반환

1  Supervisor가 실패 단계와 검증된 직전 입력을 저장하고 불완전 출력을 폐기
2  Recovery가 같은 입력으로 실패한 에이전트만 한 번 재실행
3  성공하면 출력 형식 검사와 필요한 서버 계산을 수행하고 Critic 검증으로 진행
4  Critic 자체가 실패한 경우에도 검증을 건너뛰지 않고 Critic 단계를 한 번 재실행
5  재실패하면 Supervisor가 해당 단계 종료
6  시장 코스 실패이면 검증된 배편과 요금만 유지하고 코스 이용 불가 표시
7  배편 조회 자체가 실패했고 검증된 배편 결과가 없다면 요청 실패 처리

오류에 포함된 DB와 외부 API 원인은 해당 FT 정책으로 분류  
같은 DB 오류를 FT-03으로 처리한 뒤 FT-02 예산으로 다시 호출하지 않음

## 6 FT-03 배편 조회와 시장 조회 및 갱신 저장의 DB 연결 오류

감지  연결 예외와 연결 종료 또는 3초 조회 제한 초과  
정상 조회 결과 0건은 오류가 아니라 배편 없음 또는 시장 후보 없음

1  오류를 받은 Recovery가 실패 연결을 버리고 완료되지 않은 트랜잭션을 롤백
2  1초 뒤 새 연결로 SELECT 1을 확인하고 원래 읽기 작업을 한 번 수행
3  원래 조회에 필요한 레코드까지 읽혀야 복구 성공
4  갱신 쓰기 오류는 같은 refresh_job_id와 자료 개정 번호로 재처리
5  동일 작업 ID가 이미 커밋됐다면 중복 저장하지 않고 저장된 개정 번호를 확인
6  재연결이나 원래 조회가 다시 실패하면 DB_UNAVAILABLE과 HTTP 503 반환
7  시장 조회만 실패했다면 이미 검증된 배편 영역을 유지하고 코스 영역만 실패 표시
8  운항표 저장 실패는 기존 활성 버전을 유지하고 갱신 실패 알림

복구 증거는 상태 확인 성공뿐 아니라 원래 요청 결과의 재조회 성공  
MVP에서는 DB 장애를 검증되지 않은 메모리 스냅샷으로 우회하지 않음

## 7 FT-04 코스 출력 형식 오류와 Critic 품질 반려

시점  Planner 출력 수신 직후 화면 반환 전  
형식 검사  JSON 파싱과 필수 필드 및 자료형 검사  
필수 정보  선택 배편 ID와 자료 개정 번호 및 market_id와 place_id 목록 및 방문 순서와 source_id  
품질 검사  허용 후보 존재와 시장 연계 및 중복 방문과 서버 시간 및 요금 일치와 출처 연결 검사

1  형식 검사가 실패하면 OUTPUT_SCHEMA_INVALID와 잘못된 필드 목록을 생성
2  형식은 맞지만 장소나 계산 근거가 틀리면 Critic이 RESULT_EVIDENCE_MISMATCH로 반려
3  Supervisor가 Planner 수정 예산을 확인
4  Recovery는 검증된 후보 목록과 서버 계산값 및 오류 목록을 첨부해 Planner에 한 번 수정 요청
5  수정 결과를 같은 형식 검사와 서버 검증 도구 및 Critic으로 다시 확인
6  통과하면 수정 결과 반환  다시 실패하면 COURSE_INVALID로 종료하고 배편만 유지
7  Planner가 이미 예외 복구로 추가 실행을 사용했다면 형식 오류에 추가 수정은 허용하지 않음

Critic은 금액과 배 시간을 직접 덮어쓰지 않음  
원천 가격이 없는 경우는 UNKNOWN이며 모델에 가격을 채우라고 요구하지 않음  
품질 반려는 추가 시나리오로 별도 기록하고 네 가지 필수 FT 결과와 구분

## 8 사용자 응답과 알림 및 증거

| 최종 상태 | 사용자 표시 | 복구 집계 |
|---|---|---|
| SUCCESS | 검증된 배편과 시장 코스 | 장애를 겪고 전체 필수 검증을 통과했으면 자동 복구 성공 |
| PARTIAL | 검증된 배편과 요금  시장 코스는 이용 불가 | 전체 코스 복구 성공으로 세지 않음 |
| NEEDS_CONFIRMATION | 만료와 권한 또는 정보 부족 이유 및 출처 시각 | 정상 확인 결과로 세지 않음 |
| FAILED | 요청 처리 불가와 문의용 trace_id | 미복구 |

갱신은 별도 작업이므로 신규 갱신 복구와 이전 유효 버전 제공 성공을 따로 측정  
자동 복구율과 평균 복구시간 수치 목표는 PRD의 팀 회의 빈칸 유지  
기록  trace_id와 incident_id 및 refresh_job_id와 stage 및 error_code와 attempt와 recovery_action 및 source_revision과 injected_at 및 detected_at과 recovery_started_at 및 verified_at과 final_status  
비밀번호와 키 및 사용자 입력 원문은 로그에 남기지 않음  
재시도 소진과 권한 오류 및 유효한 운항 자료 부재는 수동 개입 알림 대상  
운영 알림은 백엔드의 비동기 메일 작업으로 담당자에게 전송하고 실패하면 한 번 재전송 후 로그 보관  
메일 전송 실패가 사용자 요청을 다시 실행시키지 않음  
CI 실패는 GitHub Actions 기록과 이메일로 알림  GitHub Actions를 실시간 서비스 감시기로 가정하지 않음  
DB 장애는 서버 담당  원천 권한과 갱신 오류는 데이터 담당  에이전트와 배포 오류는 통합 담당에게 전달  
담당자 이름과 이메일 및 메일 연결 설정은 배포 환경에서 입력하고 저장소에 비밀 값을 넣지 않음

## 9 재현 시험과 통과 기준

시험용 Docker Compose에서 정상 입력과 고정 자료로 먼저 기준 응답 확인  
시험용 장애 주입 옵션은 운영 환경에서 비활성화하고 공개 API로 노출하지 않음  
각 시험은 고유 trace_id로 기록하고 한 번에 하나의 장애만 주입  
필수 장애 유형 각각 최소 3회 반복하며 복구 경로와 지속 실패 경로는 별도 사례로 기록  
가능하면 각 경로도 3회씩 반복하고 서로 다른 조건의 결과를 섞어 평균만 보고하지 않음

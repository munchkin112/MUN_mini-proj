# 1. 서비스 선정

## 1.1 서비스와 의존 대상

학습자가 주제를 입력하면, 서비스는 비동기로 객관식 문제 3개와 선택지·정답·해설을 생성해 반환한다. 요청 직후 ID와 상태를 받고 로컬 클라이언트가 조회 API를 잠정 1초 간격으로 확인해 결과를 표시한다.

`학습자 → 로컬 퀴즈 서비스 → 실제 GPT-4o mini 또는 격리된 모의 생성 서비스 → 결과`

| 의존 대상 | 용도 | 실패 영향 | 모의 여부 |
|---|---|---|---|
| GPT-4o mini API | 정상 퀴즈 생성 | 오류·지연 시 생성 실패 | 정상 경로는 실제 API, 장애 실험은 별도 모의 경로 |
| 로컬 모의 서비스 | 5xx·타임아웃·연결·형식 장애 재현 | 실습 경로 중단 | 격리된 모의 서비스, 허용목록 대상에 한해 재시작 |

## 1.2 중단 영향과 현재 대응

학습자는 대기하거나 문제를 받지 못한다. 운영자는 장애 탐지·분류·복구·검증·보고가 필요하다. 실습에는 가상 주제를 사용하고 실제 개인정보를 제외한다. 월 API 예산 목표는 20달러다. 실제 운영 이력과 수동 대응 소요시간은 확인되지 않았다. 심각도는 학습 중단과 운영자 개입을 기준으로 중간으로 제안한다.

## 1.3 3일 MVP

**포함:** 주제 입력과 비동기 결과 조회, 문제 3개, 네 모의 장애, 장애별 복구, 독립 검증, 서비스 단위 회로 차단, 로컬 운영자 조회 API, 안전 중단·알림, 호출 한도·토큰 기록, Day 3 Docker 시연.

**제외:** 회원·개인화·학습 이력, 실제 개인정보, 대규모 RAG, 실제 외부 서비스 장애 주입·재시작, 정답 내용의 완전한 정확성 보장.

**환경:** Python·FastAPI 기반 로컬 실행, LangGraph 상태기계, 정상 경로 GPT-4o mini, 장애 경로 모의 서비스. 강사 지정 Day 3 배포 환경은 Docker 필수다. 정확한 시연 형식은 강사 확인이 필요하다.

# 2. 에이전트 설계

Monitor·Diagnosis·Recovery·Verification을 결정적 규칙과 코드로 처리하고 LangGraph가 상태 전이를 담당한다. 퀴즈 생성에만 LLM을 사용한다. 원인 불명 사건에 대한 LLM 보고문은 Should이며 행동 권한은 없다.

| 역할 | 입력 | 출력 | 호출 주체 | 허용 권한 | 금지 행동·실패 시 |
|---|---|---|---|---|---|
| Monitor | 사용자 요청 결과·로컬 모의 헬스 신호 | 사건·탐지 근거 | Orchestrator | 상태 조회, 사건 생성 | 설정 변경·복구 금지; 관찰 실패 기록 |
| Diagnosis | 사건·상태 코드·예외·형식 검사 | 유형·근거·정책 | Orchestrator | 규칙 분류 | 직접 변경 금지; 미분류 시 중단·알림 |
| Recovery | 분류·정책·남은 시간 | 시도 결과 | Orchestrator | 제한 재시도·재생성·허용목록 로컬 모의 서비스 재시작 | 허용목록 밖 재시작·임의 명령 금지; 실패 시 중단 |
| Verification | 대상·형식 기준 | 별도 검증 요청·결과 | Orchestrator | 새 모의 헬스 및 생성 확인 요청, 형식 검사 | Recovery 응답 재사용 금지; 실패는 미복구 |
| Orchestrator | 사건·회로·시도·시간 | 상태 전이·종료 | Monitor 또는 사용자 | LangGraph로 정책 내 단계 호출·차단 | 한도 우회 금지; 시간 만료 시 안전 중단 |
| Notification | 최종 사건·차단 상태 | 운영자 표시 | Orchestrator | 로컬 조회 API·로그에 기록 | 정책 변경 금지; 기록 실패도 보고 |

협업: 요청·프로브 → 탐지 → 규칙 진단 → 유형별 복구 → 별도 요청을 통한 독립 검증 → 정상 복구 또는 중단·알림. 학습자 대체 결과는 복구 성공과 구분한다.

# 3. 자율성과 통제

## 3.1 자동 실행

정책에서 허용한 제한 재시도·재생성, 주제 일치 대체 문제 제공, 허용목록에 등록된 로컬 모의 서비스만 1회 재시작, 헬스 확인, 독립 검증, 회로 차단과 알림을 자동으로 수행한다. 각 사건 복구 행동은 최초 요청 이후 최대 3회다.

## 3.2 사람 승인과 금지

열린 회로 재개(Should), 허용목록·설정 변경, 새 복구 행동 추가, 실제 API를 이용한 추가 독립 생성 검증은 사람 승인이 필요하다. 허용목록 밖 및 실제 외부·운영 서비스 재시작, 임의 생성 명령, 인증정보·운영 데이터 변경, 무제한 호출은 금지한다.

## 3.3 시도·대기와 전체 제한

| 항목 | 잠정 제안값과 근거 |
|---|---|
| 5xx 복구 | 최초 요청 이후 최대 3회, 사용자와 합의한 상한. 잠정 대기 0.5·1·2초는 반복 부하와 전체 시간을 줄이기 위한 값 |
| 형식 오류 | 재생성 최대 2회, 반복 비용을 제한하기 위한 값 |
| 연결 실패 | 허용목록 로컬 모의 서비스 1회 재시작, 잠정 4초 헬스 대기. 변경 범위와 대기 제한 |
| 단일 요청 | 잠정 6초. 첫 결과 대기를 줄이기 위한 가정 |
| 사용자 대체 | 첫 6초 타임아웃 시 주제 일치 대체 문제를 저하 상태로 조회 가능하게 함. 클라이언트의 다음 조회에서 표시; 없으면 처리 중 후 실패 |
| 상태 조회 | 잠정 1초 간격. 로컬 클라이언트에서 빠른 상태 확인을 위한 가정이며 실측 후 조정 |
| 전체 워크플로 | 잠정 30초, 마지막 6초는 검증을 위해 보존. 24초 이후 새 복구를 시작하지 않음 |

시간과 상세 기준은 Day 2 초반 정상 응답·모의 서비스 실측 후 결정한다. 비동기 접수로 학습자는 이전 동기 계산의 47초를 요청 연결 상태로 기다리지 않는다. 대체 결과는 늦은 응답으로 덮어쓰지 않는다.

## 3.4 무한 루프와 회로 차단

요청 단위로 복구 행동을 최대 3회로 제한한다. 이와 별도로 동일 모의 의존 서비스 인스턴스에 대한 5xx·타임아웃·연결 실패가 30초 관찰창에서 연속 5회 발생하면 서비스 단위 회로를 연다. 서로 다른 사건의 실패를 포함하며 정상 생성 응답은 연속 수를 초기화한다. 형식 오류, 429, 헬스 프로브는 이 카운터에서 제외한다. 단일 사건의 상한 소진만으로 회로를 열지 않는다. 열린 동안 새 자동 생성 호출은 중단한다. 운영자가 재개하면 한 번의 독립 확인 후 성공 시 닫고 실패 시 다시 연다. 재개 기능이 없으면 열린 상태 유지·알림이 기본이다.

## 3.5 롤백 또는 안전 중단

| 복구 행동 | 변경 전 상태 | 실패 판정 | 롤백 또는 안전 중단 | 검증 |
|---|---|---|---|---|
| 사전 승인된 대체 경로 전환 | 기존 경로 식별자 | 복귀 검증 실패 | 직전 경로 복원; 자동 복귀는 Should | 복원 경로와 로그 확인 |
| 로컬 모의 서비스 재시작 | 허용목록 대상과 이전 상태 | 4초 내 헬스 실패 | 재시작 취소 대신 자동 시도 중단·알림 | 별도 헬스와 중단 상태 확인 |
| 재시도·재생성 | 사건 ID·시도 횟수 | 상한·기한·검증 실패 | 유효하지 않은 결과 폐기, 중단·알림 | 추가 자동 호출 없음 확인 |

# 4. 장애·복구 매트릭스

| 장애 | 탐지 신호 | 진단 근거 | 1차 복구 | 2차·상한 | 승인 | 성공 검증 |
|---|---|---|---|---|---|---|
| F-01 5xx | 오류 응답 | 상태 코드 | 백오프 재시도 | 최대 3회 후 중단 | 불필요 | 별도 모의 생성과 형식 검사 |
| F-02 타임아웃 | 잠정 6초 초과 | 요청 경과시간 | 일치하는 대체 문제 우선 표시 | 남은 시간 내 최대 3회; 대체 없으면 실패 안내 | 불필요 | 새 모의 생성 확인; 대체는 복구로 집계하지 않음 |
| F-03 연결 실패 | 연결 예외 | 모의 대상·상태 | 허용목록 로컬 모의 서비스 재시작 | 1회·헬스 최대 4초 후 중단 | 불필요 | 별도 헬스·새 모의 생성 |
| F-04 형식 오류 | 3문제·4선지·정답·해설 규칙 위반 | 결정적 검사 | 새 요청으로 재생성 | 최대 2회 후 중단 | 불필요 | 새로운 모의 생성 응답 독립 검사 |
| F-05 429 | HTTP 429 | 상태 코드·가능한 재시도 지시 | 한도 초과 분류·알림 | 즉시 자동 재시도 중단 | 별도 실제 API 확인에 필요 | 운영자 확인 후 별도 요청 |

반복 실패와 시도 소진은 장애 유형이 아닌 각 사건의 결과다. 429 모의 재현과 회로 수동 재개는 Should다.

# 5. 검증

## 5.1 복구 성공 지표

| 지표 | 정상·성공 기준 | 측정 위치 | 실패 기준 |
|---|---|---|---|
| 헬스체크 | 허용된 로컬 모의 대상이 정상 응답 | 독립 Verification | 응답 실패 또는 잠정 4초 초과 |
| 문제 형식 | 정확히 3문제, 문제당 서로 다른 A–D 선택지 4개, A–D 정답 1개, 한국어 문제·해설 | 새로운 모의 생성 확인 응답 | 하나라도 누락·형식 위반 |
| 자동 복구 성공률 | 독립 검증 성공 사건 수 / 전체 주입 사건 수 | 사건 로그 | 대체·실패·미검증은 성공에 포함하지 않음 |
| 에스컬레이션율 | 사람 개입 필요로 알린 사건 수 / 전체 주입 사건 수 | 사건·알림 로그 | 기록 누락 시 산출 불가 |
| 시간 제한 | 접수 후 30초 안에 복구·검증 종료 또는 중단 | 요청·사건 시각 | 제한시간 초과 또는 미검증 |

한국어 자동 판정은 문제와 해설에 한글 음절이 각각 하나 이상 있는지 확인한다. 형식 검사는 정답의 사실성과 언어의 자연스러움을 보장하지 않아 사람이 데모를 확인한다. Verification은 Recovery 응답을 재사용하지 않고 **새 모의 헬스와 고정 가상 주제의 생성 확인 요청**을 수행한다. 모의 확인에는 실제 모델 비용이 없고, 실제 API를 별도로 검증하면 승인 및 호출 한도에 포함한다.

## 5.2 MTTD·MTTR

모니터는 모의 서비스에 잠정 2초마다 헬스 프로브를 보내고 사용자 요청 결과도 관찰한다. 장애 상태 주입 시각과 해당 신호를 최초로 인식한 시각의 차이를 탐지시간으로 삼는다. 헬스로 5xx·형식 오류를 식별할 수 없으면 지정된 모의 기능 요청 시 탐지하며, 기능 요청 시각도 기록한다. MTTD는 탐지된 건의 평균이고 미탐지 건수·관찰 종료시간과 신호 경로를 별도 보고한다. MTTR은 독립 검증 성공 시각에서 주입 시각까지의 평균이며, 성공 건수와 미복구 건수를 함께 보고한다. 대체 결과는 정상 복구가 아니다. 모의 검증 성공을 실제 API 정상화의 증거로 사용하지 않는다.

## 5.3 로그와 비용

사건·사용자·검증 요청 ID, 실제·모의 경로, 주입·탐지·시도·검증 시각, 진단 근거, 전략·횟수, 회로 상태, 대체 여부, 운영자 알림, 실제 API 입력·출력 토큰을 기록한다. API 키·인증정보·실제 개인정보·전체 입력 원문은 기록하지 않는다. 로그 위치와 보존 기간은 [미결정]. 실습당 실제 API 호출은 최대 100회로 제한하고 운영자가 재설정한다. 계정 전체 청구 한도는 별도 확인한다.

## 5.4 데모와 반복 횟수

F-01~F-04를 각 5회씩 총 20회 실시한다. 시나리오별 4회는 복구 가능한 모의 조건, 1회는 지속 실패 조건으로 구성한다. 독립 검증 성공과 안전 중단·알림을 각각 관찰하고 주입·기능 요청·탐지·검증 시각을 기록한다. 회로 차단은 별도 확인에서 두 사건 이상에 걸친 동일 인스턴스의 5번째 실패로 열린다. 429 모의 재현은 Should다. 5회는 실습 표본이며 통계적 신뢰성을 보장하지 않는다.

서비스 요구사항과 이후 검증 방법을 정의한다. Day 2 초반 수치를 실측해 확정하고, Day 3 Docker 환경 시연을 목표로 한다. 구현 작업목록, 코드, 테스트와 배포 파일은 이후 단계의 산출물이다.

# 7. 최종 범위 선언

**Must:** 정상 퀴즈·비동기 상태, 네 장애, 차별화된 복구·독립 검증, 회로 차단·운영자 조회·알림, 대체 결과 구분, 호출 상한·토큰 로그, Docker 시연.

**Should:** 429 모의 재현, 수동 회로 재개, 대체 경로 자동 복귀, 원인 불명 LLM 보고문, 자동 비용 추정.

**성공 기준:** 3문제·4선지·A–D 정답·한국어 문제/해설의 형식을 결정적으로 검사하고, 네 장애를 각 5회 반복해 복구 가능 4회는 독립 검증 성공, 지속 실패 1회는 안전 중단·알림을 입증한다. 이 값은 계획이며 실행 결과가 아니다.

| 위험 | 영향 | 대응 |
|---|---|---|
| 부정확한 문제·해설 | 잘못된 학습 | 사람이 데모 결과 확인; 형식 검증과 구분 |
| 실제 API 비용·접근 | 실습 중단·예산 소진 | 100회 호출 상한·토큰 로그; 계정의 실제 사용량 별도 확인 |
| 역할·복구 기능 과다 | 3일 범위 초과 | 결정적 역할, Must/Should 구분; 부족하면 Must 범위 재협의 |
| 정책 수치 부정확 | 불필요한 타임아웃·대기 | Day 2 초반 실측 후 변경 |

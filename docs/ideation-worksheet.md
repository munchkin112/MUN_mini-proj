# 1. 서비스 선정

## 1.1 서비스 정의

학습자가 학습 주제를 입력하면 서비스는 객관식 문제 3개와 각 문제의 선택지, 정답, 해설을 반환한다.

정상 흐름: 학습자 → 퀴즈 생성 서비스 → 문제 생성 의존 서비스 → 문제·정답·해설 반환.

| 의존 대상 | 용도 | 실패 시 영향 | 모의 구현 여부 |
|---|---|---|---|
| 문제 생성 서비스 | GPT-4o mini를 이용한 퀴즈 생성 | 요청 실패, 지연 또는 잘못된 결과 | 장애 실습은 모의 서비스 사용; 실제 API도 사용 |

## 1.2 중단 영향

- 사용자: 문제를 받지 못하거나 응답을 오래 기다릴 수 있다.
- 운영자: 장애 탐지, 원인 확인, 복구와 정상화 확인이 필요하다.
- 데이터·비용·보안: 실습에는 가상 주제와 데이터를 사용한다. 실제 개인정보는 MVP에서 제외한다. GPT-4o mini 사용을 선택했고 API 예산은 월 최대 20달러다.
- 심각도: [미결정].

## 1.3 현재 대응 방식

실제 운영 이력은 제공되지 않았다. 장애를 사람이 발견·진단·복구·검증·보고하는 현재 절차와 소요시간은 [미결정]이다. 자동화할 절차는 모의 환경의 탐지·진단·허용된 복구·독립 검증을 중심으로 정의할 예정이다.

## 1.4 3일 MVP

**포함:** 주제 입력, 객관식 문제 3개와 해설 반환, 최소 3가지 장애 재현, 탐지·진단·복구·독립 검증, 복구 실패 시 사람에게 알림.

**제외:** 회원가입, 학습 이력·통계, 개인별 맞춤 학습, 실제 개인정보 사용, 문제의 정답성을 완전히 보장하는 기능.

**환경과 기술:** 개인 PC의 로컬 Python 실행환경과 모의 의존 서비스를 사용한다. GPT-4o mini 실제 API를 사용하며 월 예산은 20달러다. Python, FastAPI, LangChain, LangGraph, RAG는 팀이 학습한 기술이며 세부 적용 범위는 PRD 제안에 따른다.

**장애 후보:** HTTP 5xx, 응답 지연·타임아웃, 서비스 연결 실패, 동일 장애 반복. 모의 의존 서비스를 통해 로컬 격리 환경에서 재현한다.

# 2. 에이전트 설계

다음 역할은 논의용 제안이다. 별도 LLM 에이전트 또는 규칙 기반 단계로 구현할지와 책임·권한은 [미결정]. 복구와 검증은 독립적으로 수행한다.

| 역할 후보 | 책임 | 입력 | 출력 | 허용 권한·실패 시 행동 |
|---|---|---|---|---|
| 탐지 | 서비스 상태와 오류 신호 관찰 | 상태·오류 신호 | 장애 사건 | [미결정] |
| 진단 | 증거에 따른 장애 유형 분류 | 사건·관찰 근거 | 장애 유형·복구 제안 | [미결정], 판단 불가 시 사람에게 전달 제안 |
| 복구 | 허용된 정책에 따른 복구 | 진단 결과·정책 | 복구 시도 결과 | [미결정] |
| 검증 | 복구 후 상태와 핵심 기능 독립 확인 | 복구 결과·검증 기준 | 성공·실패와 근거 | [미결정] |
| 오케스트레이션 | 상태·순서·시도 제한 관리 | 사건과 각 단계 결과 | 다음 단계·최종 상태 | [미결정] |
| 알림 | 필요 시 운영자에게 결과 전달 | 실패·승인·검증 정보 | 알림 | 필요 여부·방식 [미결정] |

협업 흐름 제안: 장애 발생 → 탐지 → 진단 → 허용된 복구 → 독립 검증 → 성공 보고 또는 실패 시 사람에게 전달. 독립 검증 결과 없이 복구 성공을 선언하지 않는다.

# 4. 장애·복구 매트릭스

| 장애 유형 | 탐지 신호 | 진단 근거 | 복구 방향 | 최대 시도·승인 | 성공 검증 |
|---|---|---|---|---|---|

| 응답 지연·타임아웃 | 시간 내 응답 없음 | 경과 시간·요청 결과 | 요청 중단 후 제한적 재시도 | 최초 요청 이후 최대 3회, 승인 불필요 | 정상 응답 및 제안한 시간 기준 확인 |

| 동일 장애 반복 | 연속 실패 | 사건과 시도 이력 | 자동 시도 중단 후 사람에게 알림 | 복구 3회 실패 후 차단, 재개 시 사람 승인 | 중단 상태와 알림 확인 |

# 5. 검증

## 5.1 성공 판정

독립 검증에서 서비스 상태와 실제 퀴즈 생성 흐름을 확인한다. 응답에는 문제 3개와 각 문제의 선택지·정답·해설이 있어야 한다. 정답의 내용적 정확성은 형식 검증만으로 보장할 수 없으며 데모 결과에 대한 사람의 확인을 제안한다. 정상 시간 기준과 검증 실패 기준은 [미결정].

## 5.2 시간 측정

장애 주입·탐지·복구 시작·정상화 시각을 기록하는 방향을 제안한다. 각 사건의 탐지 시간은 탐지 시각에서 장애 주입 시각을 뺀 값, 정상화 시간은 정상화 시각에서 장애 주입 시각을 뺀 값이다. 여러 사건에 대한 평균 MTTD·MTTR의 집계 범위와 측정 위치는 [미결정].

## 5.3 로그와 데모

사건·추적 식별자, 장애 및 탐지 시각, 진단 근거, 복구 시도와 결과, 승인 여부, 독립 검증 결과, 최종 상태를 기록하는 방향을 제안한다. 저장 위치, 보존 기간, 민감정보 제거 방식은 [미결정].

최종 데모의 후보는 5xx, 타임아웃, 연결 실패, 반복 장애와 자동 시도 중단이다. 구체적 주입 방법과 성공 증거는 [미결정].

# 6. 3일 범위

프로젝트 기간은 3일이며 실행환경은 개인 PC의 로컬 환경이다. 이 문서는 서비스 요구사항과 검증 기준을 정리하며, 세부 구현 일정과 작업목록은 포함하지 않는다.

# 7. 최종 범위 선언

**반드시 포함:** 퀴즈 생성, 최소 3가지 장애 시나리오, 허용된 복구와 독립 검증, 반복 실패 시 사람에게 알림.

**제외:** 회원가입·학습 이력·통계·개인별 맞춤 기능, 실제 개인정보, 정답 정확성의 완전 보장.

**성공 기준:** 정상 요청에서 문제 3개와 필수 항목이 반환되고, 선택한 장애 시나리오의 복구 또는 안전 중단 결과를 독립적으로 판정할 수 있어야 한다. 구체적 수치와 반복 횟수는 [미결정].

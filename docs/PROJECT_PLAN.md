# 한강버스 여행 코스 프로젝트 기획서

이 문서는 네 명이 4~5일 동안 같은 목표로 움직이도록 제품 흐름과 역할 및 일정을 정리합니다  
괄호 안은 아직 팀이 확인해야 하는 제안입니다

## 1  프로젝트 목표

사용자가 한강버스 배편을 고르고 도착 예정 시각과 요금을 확인한 다음 도착지에 연계된 전통시장 먹거리 코스를 추천받아 계획할 수 있게 합니다

첫 버전은 실제로 자료를 확인할 수 있는 노선과 도착지만 다룹니다  
정확한 운항 정보와 장소 정보를 확보할 수 없으면 없는 정보를 만들어 시연하지 않고 이유를 표시합니다

## 2  사용자 흐름

| 순서 | 사용자 행동 | 화면이 보여줄 정보 |
|---|---|---|
| 1 | 날짜와 출발 및 도착 선착장과 시간 및 예산을 선택 | 자료로 지원 가능한 선택 버튼과 검색 버튼 |
| 2 | 배편을 비교 | 출발 시각과 도착 예정 시각 및 기준 요금과 자료 확인 시각 |
| 3 | 배편을 선택 | 선택한 경로와 요금 계산 기준 |
| 4 | 전통시장 먹거리 코스 추천 요청 | 도착지와 연결된 시장 및 방문 순서와 추천 이유 |
| 5 | 추천 결과 확인 | 방문 순서와 이동 예상 시간 및 확인된 가격과 출처 |
| 6 | 자료가 부족한 경우 | 어떤 정보가 빠졌는지와 공식 안내 확인 방법 |

먹거리 코스는 도착 선착장 주변 전통시장과 실제로 확인된 먹거리 정보를 연결  
확인된 시장과 업소 및 메뉴 자료로 먹거리 코스를 구성
첫 버전은 전통시장 연계에 집중

## 3  화면과 서버의 역할

| 구성 | 맡는 일 |
|---|---|
| 화면 | 출발 조건과 배편 및 코스 선택과 결과 표시 |
| 서버 | 공식 자료 조회와 저장 자료 정리 및 시간과 요금 계산 |
| 추천 기능 | 서버가 확인한 장소만 사용해 순서와 추천 이유 구성 |
| 데이터 저장소 | 배편과 선착장 및 요금과 장소 정보와 출처 및 적용 날짜 보관 |

AI가 배 시간이나 가격을 임의로 만들지 않도록 시간과 가격 계산은 서버가 담당  
추천 결과에는 사용한 장소의 자료와 확인 시각을 함께 표시

## 4  네 명 역할 제안

실명과 세부 담당은 팀원 경험에 맞춰 정합니다

| 담당 | 주 업무 | 다른 담당과 맞출 내용 |
|---|---|---|
| 1  데이터와 기획 | 시간표와 요금 및 시장 자료 확인과 사용 가능 범위 정리 | 자료 이름과 출처 및 적용 날짜를 서버 담당에게 전달 |
| 2  서버와 데이터 저장 | 자료를 저장하고 배편 검색 및 도착 시간과 요금 계산 | 화면 담당과 요청 및 응답 항목을 합의 |
| 3  화면과 사용 흐름 | 선착장과 배편 및 시장 코스 요청과 결과 화면 구현 | 서버 담당과 화면에서 필요한 자료를 합의 |
| 4  기능 개발과 배포 | 기능 하나를 주 담당으로 구현하고 Docker와 EC2 배포 및 통합 | 첫날 간단한 실행을 확인하고 개발 중간마다 팀 결과를 합침 |

배포 담당도 기능 하나의 개발 책임을 함께 맡음  
배포 확인은 마지막 날에 몰지 않고 첫날 간단한 화면을 띄우는 것으로 시작

## 5  4~5일 진행 제안

| 일정 | 팀이 함께 끝낼 일 |
|---|---|
| 1일 차 | 핵심 사용자 흐름 확정  자료 사용 권한과 제공 방식을 조사  한 노선 및 도착지 후보 선택  화면과 서버 실행 확인  첫 배포 경로 확인 |
| 2일 차 | 운항과 요금 자료를 저장하고 배편 검색 구현  화면의 선택 흐름 구현  날짜와 요금 계산 기준 연결 |
| 3일 차 | 시장과 먹거리 자료를 연결  추천 결과와 출처 표시  화면과 서버를 함께 통합 |
| 4일 차 | 출발과 도착 시간 및 가격과 코스 순서를 실제 자료로 확인  자료 누락과 서비스 장애 안내  배포 환경에서 전체 흐름 점검 |
| 5일 차가 있으면 | 사용자 관점에서 시연 연습  발견된 문제 수정  발표 내용과 최종 배포 확인 |

4일 일정이면 5일 차 검토와 발표 준비를 4일 차에 포함  
매일 작업이 끝나기 전에 각자 기능을 공유 가능한 상태로 합침

## 6  첫 버전 완료 조건

- 사용자가 날짜와 선착장을 골라 배편을 찾을 수 있음
- 배편 출발과 도착 예정 시각 및 요금이 근거 자료와 일치
- 사용자가 선택한 배편의 도착지와 연계된 전통시장 먹거리 코스를 추천받을 수 있음
- 먹거리 코스에 도착지 주변 전통시장 정보가 포함
- 추천 장소와 확인된 이동 시간 및 가격에 출처가 연결
- 확인할 수 없는 정보는 확인 필요로 표시
- 팀원 각자가 같은 안내에 따라 실행할 수 있고 통합 배포에서 주요 흐름이 열림

## 7  먼저 확인할 위험

### 운항 정보의 자동 수집과 저장

서울시 공지에서 한강버스 운항 정보와 시간표를 확인할 수 있으나 공개 개발자 API와 자동 수집 및 재사용 허용 여부는 별도 확인이 필요  
허용된 API가 없으면 공식 자료를 사용할 수 있는 범위와 갱신 방식을 확인한 뒤 수동 반영이나 다른 허용 자료를 검토

### 도착지 주변 자료의 정확성

전통시장 이름만으로 시장 안의 개별 먹거리와 가격 및 영업시간을 알 수 있다고 가정하지 않음  
장소와 메뉴 및 운영 정보를 확인할 수 있는 자료를 확보한 범위에서 추천

### 일정 계산의 신뢰도

도착 예정 시각은 운항표 기준과 실제 운항 정보를 구분  
도보나 장소 간 이동 예상 시간에 근거가 없으면 정확한 도착을 보장하지 않음

## 8  첫날에 팀이 결정할 일

- 실제로 다룰 출발지와 도착지 한 구간
- 시간표를 받을 수 있는 공식 자료와 저장 및 표시 허용 범위
- 요금 계산에 필요한 인원과 연령 기준
- 시장 주변에서 확인할 먹거리 장소와 가격 자료
- 코스에 넣을 장소 수와 한 코스의 예상 길이
- 데이터베이스와 배포 환경
- 4명 역할 배정과 매일 통합 시각

기술 세부와 조사 결과는 [데이터 조사 문서](API_EVIDENCE.md)와 [구현 참고 문서](IMPLEMENTATION_SPEC.md)에서 확인

## 9 서비스에 연결한 자동 복구

AutoHealing(장애 자동 복구)은 FastAPI 백엔드의 요청 처리 흐름과 자료 갱신 작업에 배치  
Supervisor(작업 관리자)가 재시도 예산과 종료를 결정하고 Recovery(복구 모듈)가 허용된 동작만 실행  
Critic(결과 검증 담당)은 복구된 자료와 추천 결과를 서버 검증 도구로 다시 확인  
Recovery는 Python 모듈이며 별도 LLM 에이전트 수에 포함하지 않음

정상 흐름  배편 조회 → 배편 선택 → 저장된 시장 자료 조회 → Planner 시장 코스 생성 → Critic 검증 → Supervisor 결과 반환  
오류 흐름  오류 감지 → Supervisor 복구 허용 판단 → Recovery 한 번 재시도 → 자료 및 계산 재검증 → Critic 검증 → Supervisor 성공 또는 실패 종료  
자료 갱신 흐름  관리자가 갱신 실행 → 허용된 외부 자료 조회 → 형식과 적용일 검사 → 새 버전 저장 → 저장 자료 재조회 확인

| 시점과 장애 | 감지 방법 | 자동 복구와 재시도 | 최종 처리 |
|---|---|---|---|
| 자료 갱신 중 외부 응답 지연 FT-01 | 외부 연결이 10초를 넘으면 취소하고 SOURCE_TIMEOUT 기록 | 1초 대기 후 같은 조회를 한 번 재시도  두 번째도 실패하면 이전 버전의 권한과 적용기간 및 만료시각 검사 | 유효 버전은 확인 시각을 표시해 계속 제공  만료되거나 유효성 미확인은 확인 필요로 표시하고 배편 선택 차단  기존 버전을 최신으로 덮어쓰지 않음 |
| 시장 코스 생성 중 에이전트 예외 FT-02 | 실행 래퍼가 실행 예외 또는 10초 초과를 잡고 단계와 오류 코드 기록 | Supervisor가 이전 단계의 검증된 입력으로 실패 단계만 한 번 재실행  불완전 결과는 폐기 | 재실패하면 해당 단계 종료  검증되지 않은 시장 코스는 반환하지 않음 |
| 배편 또는 시장 조회 및 갱신 저장 중 DB 오류 FT-03 | 연결 예외와 3초 조회 제한 초과를 포착  빈 조회 결과와 연결 장애를 구분 | 실패 연결을 닫고 1초 뒤 새 연결로 원래 읽기 또는 트랜잭션을 한 번 재시도  저장은 갱신 작업 ID로 중복 방지 | 재실패하면 해당 기능에 503과 DB_UNAVAILABLE 반환  임의 자료나 검증 안 된 메모리 자료로 대체하지 않음  갱신은 롤백하고 이전 버전 유지 |
| Planner가 코스를 반환하는 순간 형식 오류 FT-04 | JSON 파싱과 Pydantic(데이터 형식 검사)에서 필수 필드와 자료 식별값 및 출처 누락 감지 | Recovery가 오류 목록과 허용 장소 목록으로 Planner에 한 번 수정 요청 | 재실패하면 COURSE_INVALID로 종료  형식이 맞아도 Critic 검증 전에는 성공 아님 |
| Critic이 장소와 금액 및 시간을 검증하는 순간 품질 오류 | 미등록 장소와 출처 불일치 및 서버 계산값 차이를 검증 도구로 비교 | Planner 수정 예산이 남았으면 한 번 수정하고 다시 검증 | FT-04 수정과 품질 수정은 같은 예산 공유  모두 합쳐 수정은 한 번  모르는 가격이나 시간은 UNKNOWN으로 표시 |

외부 API는 사용자 배편 검색마다 호출하지 않고 허용된 자료 갱신에 사용  
공식 API를 확보하지 못한 경우 허용 파일 반영을 사용하며 FT-01은 외부 연결 경계의 모의 시험이라고 명시  
외부 경로 API의 실제 사용과 권한은 미확정이며 확보 전에는 실시간 도보 조회가 구현됐다고 표시하지 않음  
잘못된 사용자 입력과 배편 없음 및 자료 권한 불허는 재시도하지 않고 각각 입력 수정 또는 결과 없음 또는 확인 필요로 종료  
자세한 실행 순서와 시험 방법 및 기록 항목은 [자동 복구 상세 설계](AUTOHEALING_DESIGN.md) 참고

배편 조회 성공 뒤 시장 코스 생성이 실패하면 검증된 배편과 요금은 유지하고 시장 코스 영역만 이용 불가로 표시  
배편 유지도 자료의 권한과 적용기간이 유효한 경우에만 허용  
갱신 실패 뒤 이전 유효 자료를 제공한 경우는 자료 갱신 복구와 구분해 기록  
복구율에는 모든 필수 장애 시험을 포함하며 PARTIAL과 유효성 미확인은 전체 코스 복구 성공으로 세지 않음


복구 설계와 FT-01~04 시험 구현은 서버 담당과 통합 담당이 함께 수행
세부 역할은 PRD 팀 정보에서 확정하고 첫날 정상 경로와 오류 계약부터 통합

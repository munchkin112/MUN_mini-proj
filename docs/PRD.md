# 한강버스 여행 코스 PRD 1 pager

문서 목적  팀이 첫 버전의 고객과 범위를 함께 이해하기 위한 기획 초안  
기획 방식  고객이 얻을 가치부터 정리하는 AWS Working Backwards 방식

## 고객에게 전하는 안내

### 배편을 고르고 도착지 코스까지 한 번에

한강버스로 나들이를 준비할 때 출발 시각과 요금 그리고 도착한 뒤 갈 곳을 따로 찾아야 하는 번거로움을 줄입니다  
사용자는 날짜와 선착장을 고르고 배편을 선택한 뒤 도착 예정 시각과 요금을 확인합니다  
이후 데이트 코스 또는 전통시장 먹거리 코스 중 하나를 골라 추천받습니다

가상 고객 반응  배 시간부터 도착한 뒤 갈 곳까지 한 흐름으로 정할 수 있어요

## 고객과 핵심 가치

- 고객  한강버스로 데이트나 나들이를 계획하는 시민과 관광객
- 문제  운항 정보와 요금 및 주변 코스를 여러 곳에서 찾아 직접 조합해야 함
- 가치  선택한 배편의 도착 시각과 도착지 코스를 한 흐름으로 안내

## 첫 버전에서 제공할 경험

1  날짜와 출발 및 도착 선착장을 선택
2  배편별 출발 시각과 도착 예정 시각 및 공식 요금을 비교
3  배편을 선택하고 데이트 또는 먹거리 코스 하나를 선택
4  방문 순서와 확인된 이동 시간 및 가격과 자료 출처를 확인

먹거리 코스는 도착지 주변 전통시장과 확인된 먹거리 정보를 연결  
요금은 이용 인원과 공식 요금 구분에 따라 계산  
AI는 확인된 장소를 조합하고 추천 이유를 설명하며 시간과 요금은 서버가 계산

## 첫 버전 범위

- 실제 사용이 허용된 운항과 요금 및 장소 자료 저장
- 자료 출처와 적용 날짜 및 마지막 확인 시각 표시
- 정보가 없거나 최신 여부를 모르면 확인 필요로 안내
- 자료를 확인할 수 있는 한 노선과 도착지부터 시작

온라인 예약과 결제 및 실시간 좌석 조회는 첫 버전에서 제외

## 교과목 필수 요건과 제출

### AutoHealing(장애 자동 복구) 서비스

장애를 감지하고 원인을 판단한 뒤 재시도나 대체 경로로 복구하고 정상 응답을 다시 확인

- 역할이 분리된 에이전트 3개 이상과 Critic(결과 검증 역할) 포함
- 전체 서비스를 Docker Compose로 실행
- Kubernetes(쿠버네티스)는 사용하지 않음
- FT-01 외부 API 시간 초과
- FT-02 에이전트 실행 예외
- FT-03 데이터베이스 연결 오류
- FT-04 LLM(언어 모델) 출력 형식 오류

네 가지 장애 유형을 각각 3회 이상 시험하고 성공과 실패 및 원인을 기록  
자동 복구율은 사람의 개입 없이 복구한 시험 수를 전체 시험 수로 나눠 계산하며 네 가지 필수 유형을 모두 포함  
평균 복구시간은 장애를 주입한 시각부터 첫 정상 응답까지의 시간을 자동 복구 성공 건 기준으로 계산

### 배포 파이프라인

커밋할 때 테스트를 자동 실행하고 실패하면 배포를 막음  
테스트 실패로 배포가 차단되는 과정을 최소 한 번 증명하고 파이프라인 실패 알림을 한 개 채널에 전송

## 성공을 판단하는 방법

- 배편 선택부터 코스 추천까지 사용자가 완료할 수 있는지
- 도착 시각과 요금이 공식 자료와 맞는지
- 추천 장소와 가격 및 이동 정보에 근거가 있는지
- 정보가 부족할 때 이유를 알기 쉽게 안내하는지

목표 수치는 실제 자료를 확인한 뒤 팀이 정함

## 자주 묻는 질문

**운항 정보는 실시간인가요**  
실시간 연결 방식이 확인되기 전까지 예정 시간표로 표시하고 실제 운항과 구분

**자료를 저장해도 되나요**  
공식 API 유무와 저장 및 재사용 허용 조건을 확인한 뒤 결정  
미확인 자료는 서비스 데이터로 사용하지 않음

**가격이나 영업 여부를 모르면요**  
추정값을 만들지 않고 확인 필요로 표시

## 착수 전에 확인할 위험

운항 시간표의 최신 적용일과 자동 수집 방식 및 저장 권한을 아직 확인해야 합니다  
시장 안 먹거리의 가격과 영업 정보도 확인이 필요합니다  
확인 결과에 따라 첫 버전의 노선과 코스 범위를 정합니다

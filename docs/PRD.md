# 한강버스 여행 코스 PRD

문서 목적  팀이 첫 버전의 고객과 범위 및 완료 기준을 함께 이해하기 위한 기획 초안  
기획 방식  고객이 얻을 가치부터 정리하는 AWS Working Backwards 방식

## 고객에게 전하는 안내

### 배편을 고르고 도착지 코스까지 한 번에

한강버스로 나들이를 준비할 때 출발 시각과 요금 그리고 도착한 뒤 갈 곳을 따로 찾아야 하는 번거로움을 줄입니다  
사용자는 출발지와 도착지 및 날짜와 원하는 시간과 예산을 화면에서 직접 선택합니다  
배편을 고른 뒤 도착 예정 시각과 요금을 확인하고 도착지와 연계된 전통시장 먹거리 코스를 추천받습니다

가상 고객 반응  배 시간부터 도착한 뒤 갈 곳까지 한 흐름으로 정할 수 있어요

## 고객과 핵심 가치

- 고객  한강버스와 전통시장을 함께 방문하려는 시민과 관광객
- 문제  운항 정보와 요금 및 주변 코스를 여러 곳에서 찾아 직접 조합해야 함
- 가치  선택한 배편의 도착 시각과 도착지 코스를 한 흐름으로 안내

## 첫 버전에서 제공할 경험

1  날짜와 출발지 및 도착지를 버튼으로 선택
2  원하는 출발 시간대와 예산을 선택
3  선택 조건에 맞는 배편과 공식 요금을 비교
4  배편을 고르고 도착지 연계 전통시장 먹거리 코스를 요청
5  방문 순서와 확인된 이동 시간 및 가격과 자료 출처를 확인
6  자료가 부족하거나 유효성을 확인할 수 없으면 이유와 마지막 확인 시각을 확인

선택 목록에는 확인된 자료로 제공할 수 있는 값만 표시  
먹거리 코스는 도착지 주변 전통시장과 확인된 먹거리 정보를 연결  
요금은 서버가 인원과 공식 요금 기준에 따라 계산  
AI는 확인된 장소를 조합하고 추천 이유를 설명하며 시간과 요금은 서버가 계산

## 첫 버전 범위와 결정할 항목

첫 버전에서는 사용자가 출발지와 도착지 및 날짜와 시간과 예산을 직접 선택  
선택 가능한 값은 사용이 허용되고 출처와 적용일을 확인한 자료 안에서 제공  
온라인 예약과 결제 및 실시간 좌석 조회는 첫 버전에서 제외
시장 연계 먹거리 코스에 집중하며 별도 관광 코스는 제공하지 않음

| 팀이 확정할 항목 | 결정 내용 | 결정 기한 |
|---|---|---|
| 지원 노선과 출발지 및 도착지 | [팀 회의에서 입력] | 2026년 11월 5일 |
| 날짜와 시간 선택 가능 범위 | [팀 회의에서 입력] | 2026년 11월 5일 |
| 코스 하나에 포함할 장소 수 상한 | [팀 회의에서 입력] | 2026년 11월 5일 |
| 운항 시간표와 장소 자료의 저장 및 표시 권한 | [허용 범위와 근거 링크 입력] | 2026년 11월 4일 착수 전 |
| 네 명의 담당자 이름과 주 담당 기능 | 아래 팀 정보 표에 입력 | 2026년 11월 5일 |

자료 권한이 허용되면 공식 자료를 가져와 저장하고 출처와 적용일 및 마지막 확인 시각을 함께 표시  
저장 권한이 없으면 해당 자료를 서비스 데이터베이스에 복사하지 않음  
대체 자료도 허용되지 않으면 실제 운항 정보처럼 보이는 기능은 제공하지 않고 사용 불가 사유를 표시  
개발과 자동 시험에는 고정 테스트 자료를 사용하며 데모에 쓸 경우에도 실제 정보가 아닌 예시임을 화면에 표시  
권한이 있는 자료를 착수 전까지 확인하지 못하면 팀은 지원 범위를 줄이거나 허용된 별도 자료를 선택

## 서비스 구조와 에이전트 책임

| 역할 | 맡는 일 | 완료 판단 |
|---|---|---|
| Supervisor(작업 관리자) | 요청 흐름과 재시도 횟수 관리 및 최종 성공 또는 실패 결정 | 필수 검증을 통과한 결과만 사용자에게 전달 |
| Executor(자료 실행 담당) | 저장된 시간표와 장소 자료 조회 및 서버 계산 결과 전달 | 자료 출처와 적용일 및 계산값이 함께 있음 |
| Planner(코스 제안 담당) | 확인된 장소 후보를 사용해 방문 순서와 추천 이유 제안 | 확인되지 않은 장소나 가격을 새로 만들지 않음 |
| Critic(결과 검증 담당) | 장소가 확인 자료에 있는지와 서버 계산 시각 및 요금의 일치 및 출처 표시 검증 | 불일치나 누락이 있으면 결과를 반려 |

처리 순서  화면 요청 → Supervisor → Executor → Planner → Critic → Supervisor 최종 결정 → 화면  
Critic은 시간이나 요금을 직접 고치지 않고 오류를 표시  
계산이 필요한 시간과 요금은 Executor가 전달한 서버 계산값을 그대로 사용  
Recovery는 각 단계의 실패 때만 호출하는 백엔드 모듈이며 복구 후 Critic 검증으로 복귀  
네 역할의 책임은 겹치지 않게 두고 Supervisor만 전체 시도의 최종 상태를 결정

### 에이전트 사이에 전달할 정보

- trace_id  한 번의 요청과 로그를 연결하는 식별값
- 요청 조건  날짜와 출발지와 도착지와 선택 시간 및 예산
- 운항 식별값과 계산된 출발 및 도착 시각과 요금
- 추천 장소 식별값과 방문 순서 및 추천 이유
- 출처와 적용일 및 마지막 확인 시각
- 현재 단계와 재시도 횟수 및 오류 코드와 결과 상태

## 장애 감지와 자동 복구

AutoHealing(장애 자동 복구)은 FastAPI 백엔드의 요청 처리 흐름과 자료 갱신 작업에 배치  
Supervisor(작업 관리자)가 재시도 예산과 종료를 결정하고 Recovery(복구 모듈)가 허용된 동작만 실행  
Critic(결과 검증 담당)은 복구된 자료와 추천 결과를 서버 검증 도구로 다시 확인  
Recovery는 Python 모듈이며 별도 LLM 에이전트 수에 포함하지 않음

정상 흐름  배편 조회 → 배편 선택 → 저장된 시장 자료 조회 → Planner 시장 코스 생성 → Critic 검증 → Supervisor 결과 반환  
오류 흐름  오류 감지 → Supervisor 복구 허용 판단 → Recovery 한 번 재시도 → 자료 및 계산 재검증 → Critic 검증 → Supervisor 성공 또는 실패 종료  
자료 갱신 흐름  관리자가 갱신 실행 → 허용된 외부 자료 조회 → 형식과 적용일 검사 → 새 버전 저장 → 저장 자료 재조회 확인

| 시점과 장애 | 감지 방법 | 자동 복구와 재시도 | 최종 처리 |
|---|---|---|---|
| 자료 갱신 중 외부 응답 지연 FT-01 | 외부 연결이 10초를 넘으면 취소하고 SOURCE_TIMEOUT 기록 | 1초 대기 후 같은 조회를 한 번 재시도  두 번째도 실패하면 이전 버전의 권한과 적용기간 및 만료시각 검사 | 유효 버전은 확인 시각을 표시해 계속 제공  만료되거나 유효성 미확인은 확인 필요로 표시하고 배편 선택 차단  기존 버전을 최신으로 덮어쓰지 않음 |
| 시장 코스 생성 중 에이전트 예외 FT-02 | 실행 래퍼가 실행 예외 또는 10초 초과를 잡고 단계와 오류 코드 기록 | Supervisor가 이전 단계의 검증된 입력으로 실패 단계만 한 번 재실행  불완전 결과는 폐기 | 재실패하면 해당 단계 종료  검증되지 않은 시장 코스는 반환하지 않음 |
| 배편 또는 시장 조회 및 갱신 저장 중 DB 오류 FT-03 | 연결 예외와 3초 조회 제한 초과를 포착  빈 조회 결과와 연결 장애를 구분 | 실패 연결을 닫고 1초 뒤 새 연결로 원래 읽기 또는 트랜잭션을 한 번 재시도  저장은 갱신 작업 ID로 중복 방지 | 재실패하면 해당 기능에 503과 DB_UNAVAILABLE 반환  임의 자료나 검증 안 된 메모리 자료로 대체하지 않음  갱신은 롤백하고 이전 버전 유지 |
| Planner가 코스를 반환하는 순간 형식 오류 FT-04 | JSON 파싱과 Pydantic(데이터 형식 검사)에서 필수 필드와 자료 식별값 및 출처 누락 감지 | Recovery가 오류 목록과 허용 장소 목록으로 Planner에 한 번 수정 요청 | 재실패하면 COURSE_INVALID로 종료  형식이 맞아도 Critic 검증 전에는 성공 아님 |
| Critic이 장소와 금액 및 시간을 검증하는 순간 품질 오류 | 미등록 장소와 출처 불일치 및 서버 계산값 차이를 검증 도구로 비교 | Planner 수정 예산이 남았으면 한 번 수정하고 다시 검증 | FT-04 수정과 품질 수정은 같은 예산 공유  모두 합쳐 수정은 한 번  모르는 가격이나 시간은 UNKNOWN으로 표시 |

외부 API는 사용자 배편 검색마다 호출하지 않고 허용된 자료 갱신에 사용  
공식 API를 확보하지 못한 경우 허용 파일 반영을 사용하며 FT-01은 외부 연결 경계의 모의 시험이라고 명시  
외부 경로 API의 실제 사용과 권한은 미확정이며 확보 전에는 실시간 도보 조회가 구현됐다고 표시하지 않음  
잘못된 사용자 입력과 배편 없음 및 자료 권한 불허는 재시도하지 않고 각각 입력 수정 또는 결과 없음 또는 확인 필요로 종료  
자세한 실행 순서와 시험 방법 및 기록 항목은 [자동 복구 상세 설계](AUTOHEALING_DESIGN.md) 참고

배편 조회 성공 뒤 시장 코스 생성이 실패하면 검증된 배편과 요금은 유지하고 시장 코스 영역만 이용 불가로 표시  
배편 유지도 자료의 권한과 적용기간이 유효한 경우에만 허용  
갱신 실패 뒤 이전 유효 자료를 제공한 경우는 자료 갱신 복구와 구분해 기록  
복구율에는 모든 필수 장애 시험을 포함하며 PARTIAL과 유효성 미확인은 전체 코스 복구 성공으로 세지 않음

## 성공을 판단하는 방법

- 사용자가 지원 목록에서 출발지와 도착지 및 날짜와 시간과 예산을 선택할 수 있음
- 배편 선택부터 코스 하나 선택까지 흐름을 완료할 수 있음
- 도착 시각과 요금이 서버 계산 및 확인된 근거 자료와 일치
- 추천 장소가 확인된 자료에 있고 추천 결과에 출처와 적용일 및 마지막 확인 시각이 표시
- 네 가지 필수 장애를 각각 3회 이상 주입하고 결과와 원인을 기록
- 자동 복구율은 사람의 개입 없이 정상 응답한 횟수를 전체 장애 시험 횟수로 나눠 계산
- 평균 복구시간은 장애 주입부터 첫 정상 응답까지 자동 복구 성공 건에 대해 계산
- 자동 복구하지 못한 시험도 전체 건수에 포함하고 시나리오별 결과를 따로 보고

| 팀 회의에서 정할 복구 목표 | 합의 후 입력 |
|---|---|
| 목표 자동 복구율 | [     ] % |
| 목표 평균 복구시간 | [     ] 초 |
| 시나리오별 최소 통과 기준 | [     ] |
| 목표 합의 담당자와 날짜 | [이름 또는 역할]  [날짜] |
| 실제 측정값과 판정 | [시험 후 입력] |

수치 목표는 팀 회의에서 합의하기 전까지 임의로 정하지 않음  
측정 방식과 실제 값 및 통과 여부는 장애 복구 보고서에 남김

## CI/CD와 배포 기준

CI/CD(검사와 배포 자동화)는 GitHub Actions로 구성  
코드를 올릴 때 자동 검사를 실행하고 검사가 실패하면 EC2 배포를 막음  
검사를 통과한 main 변경분을 Docker Compose로 EC2 시연 환경에 배포  
배포 뒤 상태 확인 주소로 기본 응답을 확인하고 결과와 로그를 보관  
CI에서는 실제 LLM 호출 대신 고정된 LLM 모의 응답을 사용해 비용과 결과 변동 없이 검증  
검사 범위는 서버의 시간과 요금 계산 및 요청과 응답 형식과 추천 장소 검증 및 출처 표시와 화면의 주요 선택 흐름 및 FT-01~04 장애 재현  
각 장애는 자동 시험 자료로 재현하고 실제 API 미연결 상태에서 시험한 경우 그 사실을 보고서에 표시

| 파이프라인과 보고서 항목 | 기준 |
|---|---|
| 도구와 배포 대상 | GitHub Actions  Docker Compose  EC2 |
| 실패 알림 | GitHub Actions 실행 기록과 담당자 이메일 |
| 비밀 정보 | 저장소와 코드 및 로그에 넣지 않고 GitHub Actions 비밀 값과 EC2의 별도 환경 설정에 보관 |
| 테스트 자료 | 허용된 고정 자료와 LLM 모의 응답 및 장애 재현 입력 |
| 커버리지 기준 | [팀 회의에서 수치 입력]  수치 합의 전에는 검사 결과와 측정값을 보고 |
| 실행 증빙 | 실행 ID와 커밋 SHA 및 로그 링크와 배포 후 상태 확인 결과 |

|---|---:|

## 자주 묻는 질문

**운항 정보는 실시간인가요**  
실시간 연결 방식이 확인되기 전까지 예정 시간표로 표시하고 실제 운항과 구분

**자료를 저장해도 되나요**  
공식 자료의 저장과 표시 조건을 확인한 뒤 허용된 경우에만 저장  
미확인 자료는 서비스 데이터로 사용하지 않음

**최신 여부를 확인할 수 없으면요**  
마지막 확인 시각과 적용일을 함께 표시하고 유효성을 확인할 수 없으면 확인 필요로 안내

**가격이나 영업 여부를 모르면요**  
추정값을 만들지 않고 확인 필요로 표시

# 한강로컬패스 PRD

문서 기준  2026년 11월 2일  
문서 상태  팀 개발을 위한 설계  실제 API 연결과 배포 및 장애 시험 완료를 뜻하지 않음  
문서 목적  제품 범위와 구현 계약 및 시험과 제출 기록을 이 파일에서 함께 관리  
기획 방식  AWS Working Backwards(고객 가치부터 거꾸로 설계)  
이 파일을 현재 요구사항의 기준으로 사용하며 새 설계 문서나 복구 문서를 추가하지 않음  
기존 문서는 조사 이력으로만 참고하고 다른 내용이 있으면 이 PRD를 우선

## 1 고객에게 전하는 안내

### 배편을 고르면 도착지 전통시장 먹거리 코스까지

한강버스 나들이를 준비할 때 시간표와 요금 및 도착한 뒤 갈 곳을 따로 찾는 번거로움을 줄입니다  
사용자는 출발지와 도착지 및 날짜와 시간과 예산을 버튼으로 선택합니다  
배편별 도착 예정 시각과 요금을 확인하고 도착지 주변 전통시장 먹거리 코스를 추천받습니다

고객  한강버스와 전통시장을 함께 방문하려는 시민과 관광객  
가치  확인된 배편과 시장 방문 정보를 한 흐름으로 안내  
가상 고객 반응  배 시간과 도착한 뒤 먹거리를 함께 정할 수 있어요

## 2 확정 범위와 팀 결정 항목

### 확정한 첫 버전

- React와 JavaScript 화면  FastAPI 서버  Docker Compose 실행  EC2 배포
- 확인된 자료로 지원하는 출발지와 도착지 및 날짜와 시간과 예산을 사용자가 선택
- 배편 검색과 도착 예정 시각 및 공식 요금 안내
- 도착지에 연결된 전통시장과 확인된 업소 및 메뉴를 이용한 먹거리 코스
- 시간과 요금은 서버 코드가 계산하고 AI는 확인된 장소의 순서와 추천 이유를 구성
- Supervisor가 최종 결정  Recovery가 복구 동작 수행  Critic이 결과 검증
- 코스가 끝내 실패하면 유효한 배편과 요금은 유지하고 코스만 이용 불가로 안내

데이트와 일반 관광 코스 및 테마 선택은 MVP(첫 버전)에서 제외  
예약과 결제 및 실시간 좌석과 운항 위치 및 결항 보장과 범용 환승 최적화도 제외  
사용자별 회원가입과 즐겨찾기 및 운영 대시보드는 필수 범위에 추가하지 않음  
사용자 요청마다 홈페이지를 수집하지 않고 권한과 유효성이 확인된 저장 자료를 조회  
지원하지 않는 구간이나 확인되지 않은 장소를 임의로 생성하지 않음

## 3 사용자 흐름과 기능 완료 조건

| 단계 | 화면과 서버의 처리 | 완료 조건 |
|---|---|---|
| 조건 선택 | 지원 목록에서 출발지와 도착지 및 날짜와 시간과 예산 선택 | 서버도 허용 ID와 범위를 검사 |
| 배편 검색 | 적용일과 운항일 및 방향과 정차 순서를 검사해 배편 반환 | 선택한 날짜에 유효한 운항편만 표시 |
| 배편 선택 | 서버가 선택 배편과 자료 개정 번호를 재확인하고 요금 계산 | 예정 시각과 요금 및 출처 표시 |
| 시장 자료 조회 | 도착 선착장과 연결된 시장과 확인된 업소 및 메뉴 조회 | 시장과 업소의 관계에 근거가 있음 |
| 시장 코스 생성 | Planner가 후보 ID와 방문 순서 및 추천 이유 구성 | 새로운 장소나 가격 생성 없음 |
| 결과 검증 | Critic과 서버 도구가 형식과 자료 및 계산값 검사 | 통과한 결과만 화면에 전달 |
| 일부 실패 | 배편은 유효하나 코스 생성 또는 조회 실패 | 배편과 요금 유지  코스 영역은 실패 표시 |

정상 빈 조회는 배편 없음 또는 시장 후보 없음으로 안내하며 시스템 장애와 구분  
가격이나 영업 정보가 없으면 확인 필요 표시  
검증되지 않은 고정 코스나 기본 소개를 자동 대체하는 기능은 이번 범위에 포함하지 않음  
다른 출발지여도 같은 도착지라면 같은 시장 후보가 나올 수 있음

## 4 자료와 계산 원칙

| 자료 | 반드시 보관하거나 확인할 항목 |
|---|---|
| 선착장 | ID와 이름 및 실제 승하선 위치와 운영 적용기간 |
| 운항표 | 배편 ID와 출발 및 도착 선착장과 시각  운항일과 방향 및 정차 순서  적용기간과 개정 번호 |
| 요금 | 요금 구분과 인원 및 단가와 적용기간 및 출처 |
| 시장과 먹거리 | 시장 ID와 업소 ID 및 소속 관계  메뉴와 단위 및 확인된 가격  운영시간과 좌표의 근거 |
| 이동 근거 | 출발과 도착 지점 및 확인된 이동시간과 취득 시각 |
| 출처 | 원문 링크와 사용 허용 근거  적용일과 취득 시각 및 마지막 성공 확인 시각과 expires_at(재사용 만료시각) |

저장과 가공 및 표시가 허용된 공식 자료만 적재  
권한 불허나 미확인이면 다른 허용 자료를 검토하고 확보 전에는 실제 서비스 자료로 쓰지 않음  
고정 시험 자료는 개발과 CI에서 사용하고 데모에 쓰면 예시 자료임을 명시  
허가되지 않은 시간표에서 추출한 값을 시험 자료라는 이유로 서비스에 복사하지 않음

운항 정보는 예정 시간표 기준이며 현재 운항과 구분  
취득한 시각이 최근이라는 이유만으로 최신이라고 보장하지 않음  
기존 자료 재사용은 저장 권한과 여행 날짜 적용기간 및 만료시각이 모두 확인된 경우에만 허용  
만료시각이 없으면 무기한 유효로 보지 않고 확인 필요 표시 및 해당 배편 선택 차단  
갱신 자료는 검증한 새 개정으로 저장하고 실패하면 기존 활성 버전을 덮어쓰지 않음  
원천 응답 수신 시각과 마지막 성공 갱신 시각 및 제공 자료의 확인 시각을 구분

시각은 Asia/Seoul 기준으로 계산  
선택한 배편의 출발과 도착은 같은 운항편의 실제 정차 순서를 참조  
현재는 단일 배편을 기준으로 하며 환승이 필요한 조합은 지원 여부 확정 전 차단  
요금은 공식 단가와 구분 및 인원으로 계산하고 LLM이 숫자를 수정하지 못하게 함  
도보시간이 없으면 직선거리로 만들어 통과시키지 않음  
가격이 없으면 0원으로 더하지 않고 예산 확인 필요 표시  
인허가상 영업 상태만으로 방문일 영업을 보장하지 않음  
준비와 체류시간을 사용하면 사용자 설정값임을 표시하고 공식 운항값과 구분

공식 시간표와 시장 자료의 실제 확보 및 사용권과 대상 구간 검산은 착수 전 확인  
현재 확인하지 않은 API 인증과 저장 권한 및 현장 가격을 확보 완료라고 기록하지 않음

## 5 역할과 상태 및 전달 정보

| 역할 | 맡는 일 | 최종 권한 |
|---|---|---|
| Supervisor(작업 관리자) | 단계 실행과 예산 및 마감 관리  오류 분류와 재시도 승인 | 전체 성공과 일부 실패 및 최종 실패 결정 |
| Executor(자료 실행 담당) | 저장 자료와 허용 도구 조회  서버 계산 결과 전달 | 사용자 결과 최종 승인 불가 |
| Planner(시장 코스 제안 담당) | 허용 시장과 장소 ID로 순서 및 추천 이유 생성 | 장소와 가격 및 운항시각 생성 불가 |
| Critic(결과 검증 담당) | 서버 검증 도구로 ID와 시장 연계 및 출처와 계산 일치 확인 | 검증 반려와 이유 전달 |
| Recovery(복구 모듈) | 승인된 재시도와 재연결 및 결과 재검사 실행 | 새로운 예산이나 성공 판정 생성 불가 |

Executor와 Planner 및 Critic은 실제 지시와 입출력 및 도구 권한이 분리된 에이전트로 구현  
Supervisor는 규칙 기반 실행 관리  Recovery는 Python 모듈이며 별도 LLM 에이전트 수에 포함하지 않음  
단순 함수 이름만 에이전트로 붙여 역할 분리 완료를 주장하지 않음  
Critic도 LLM 의견만 믿지 않고 결정적 서버 검증 도구 결과를 사용  
같은 검증을 반복 실행해도 수정 예산이 새로 생기지 않음

정상 흐름  입력 검사 → Supervisor → Executor → Planner → Critic → Supervisor → 화면  
오류 흐름  단계 오류 → Supervisor 예산 확인 → Recovery → 실패 단계 재실행 → 서버 검증 및 Critic → Supervisor 종료

Handoff(업무 전달)에 포함할 정보  
trace_id(요청 추적 번호)와 incident_id(장애 번호) 및 단계와 상태  
요청 조건과 선택 배편 ID 및 자료 개정 번호  
시장과 장소 ID 및 서버 계산 시각과 요금 및 출처와 적용일 및 확인 시각  
시도 횟수와 Planner 수정 사용 여부 및 전체 deadline_at(종료 시각)과 오류 코드  
필수 필드가 없으면 다음 단계로 넘기지 않음

상태 흐름  CREATED → EXECUTING → VALIDATING → SUCCESS  
오류는 RECOVERING을 거쳐 원래 단계로 복귀하거나 PARTIAL 또는 FAILED로 종료  
원천 미확인과 가격 누락은 NEEDS_CONFIRMATION으로 표시  
상태 전달은 요청 메모리에서 관리하고 장애 증거는 DB와 독립된 구조화 로그에 남김  
DB가 실패했는데 실행 상태 저장에 성공했다고 표시하지 않음

## 6 최소 API와 화면 계약

다음은 구현할 내부 API 계약이며 실제 구현 완료를 뜻하지 않음  
동기 요청으로 시작하며 별도 비동기 실행 목록과 운영 대시보드를 필수로 추가하지 않음

| 요청 | 용도와 필수 조건 | 결과 |
|---|---|---|
| GET /api/v1/piers | 지원 출발지와 도착지 조회 | 허용 선착장과 지원 조합 |
| GET /api/v1/sailings | 출발지와 도착지 및 날짜 | 유효 배편과 출처  정상 빈 목록 허용 |
| POST /api/v1/itineraries | 선택 배편 ID와 개정 번호  날짜와 시간 및 예산 | 최종 상태와 배편 및 시장 코스와 항목별 확인 상태 |
| GET /health/live | 서버 응답 확인 | 민감 정보 없는 생존 상태 |
| GET /health/ready | DB와 필수 설정 및 자료 준비 확인 | 준비 실패 503  일시 LLM 장애와 분리 |

모든 응답은 trace_id를 포함하고 결과에는 status와 reason_code 및 자료 출처와 확인 시각 포함  
잘못된 입력 422  호출 제한 429  핵심 의존성 장애 503  전체 기한 초과 504  
검증된 배편을 유지한 일부 실패는 200과 PARTIAL 및 course_error로 구분  
배편 없음과 확인 필요는 정상 처리 결과로 표시하며 연결 장애로 바꾸지 않음  
선택 배편이 개정돼 바뀌면 409와 다시 선택 안내  
운영 갱신과 로그 조회는 별도 인증 및 서버 권한 검사를 거쳐 일반 사용자에게 노출하지 않음

## 7 입력과 권한 및 LLM 보안

- 선착장과 배편 및 시장 ID와 날짜 및 예산에 타입과 허용 목록 및 조합 검사
- 서버에서 요청 크기와 빈도 및 동시 실행과 모델 호출 예산 제한
- DB 조회는 매개변수 바인딩을 사용하고 사용자 입력이나 LLM 출력으로 임의 쿼리 생성 금지
- LLM 도구는 허용된 읽기와 검증 작업만 제공  임의 URL과 셸 및 배포 명령 권한 없음
- 자료 속 문장은 입력 데이터로 취급하고 시스템 명령으로 실행하지 않음
- JSON 형식이 맞아도 미등록 장소와 잘못된 시각 및 근거 없는 가격은 Critic이 차단
- 소개는 일반 텍스트로 표시하고 LLM이나 원문 HTML을 그대로 렌더링하지 않음
- API 키와 DB 비밀번호 및 알림 비밀 값은 서버 환경과 GitHub Actions Secrets(비밀 값 저장소)에 보관
- 오류와 로그 및 화면에 키나 원문 개인정보를 노출하지 않음
- 운영 API는 화면을 숨기는 방식에 의존하지 않고 서버에서 인증과 권한 검사
- 향후 요청 결과 조회 API를 추가하면 비회원 세션도 결과 소유권 검사
- 장애 주입은 시험 환경에서만 활성화하고 공개 서비스 요청으로 켤 수 없게 함

## 8 AutoHealing 배치와 공통 한도

FastAPI 요청 처리 안에 Supervisor와 Recovery를 배치하고 Critic으로 복구 결과를 검증  
자료 갱신도 같은 복구 정책을 사용하되 사용자 추천 요청과 작업 ID를 구분  
React에서 자동 재요청을 추가해 백엔드 재시도와 중복시키지 않음

| 설정 | 기본 실행 기준 |
|---|---|
| 외부 LLM과 에이전트 | 시도당 10초 |
| 외부 자료 연결 | 연결이 실제 확보된 경우 시도당 10초 |
| DB 연결 및 개별 조회 | 시도당 3초 |
| 재시도 횟수 | 최초 실행 뒤 실패 단계 최대 1회  총 실행 2회 |
| 대기 | 1초  남은 전체 기한 안에서만 대기 |
| 전체 요청과 갱신 작업 | 각각 시작부터 40초  재시도로 초기화하지 않음 |
| Planner 추가 실행 | 예외와 시간 초과 및 형식 오류와 품질 반려를 합쳐 최대 1회 |
| 전체 LLM 호출 | 요청당 최대 6회  단계별 한도와 전체 기한이 먼저 우선 |

SDK와 HTTP 및 DB 도구의 숨은 재시도는 끄거나 같은 예산으로 집계  
하위 연결 오류는 해당 오류 정책으로 한 번만 처리하고 상위 에이전트 예외로 다시 재시도하지 않음  
남은 시간으로 다음 시도를 할 수 없으면 추가 실행 없이 DEADLINE_EXCEEDED 종료  
늦게 온 응답은 폐기  
인증 오류와 권한 불허 및 잘못된 입력과 정상 빈 결과는 재시도하지 않음  
컨테이너나 EC2 재시작 및 자동 롤백은 필수 복구 동작에 포함하지 않음

## 9 서비스 시점별 장애 처리

### FT-01 추천 생성 중 외부 LLM API 시간 초과

운항 API 확보 여부와 무관하게 추천 과정에서 실제로 사용하는 외부 LLM API를 필수 시험 대상으로 사용  
호출이 10초 안에 끝나지 않으면 어댑터가 취소하고 LLM_API_TIMEOUT 기록  
Supervisor가 남은 시간과 Planner 예산을 확인한 뒤 Recovery가 1초 대기 후 같은 검증 입력으로 한 번 재요청  
응답이 오면 형식 검사와 서버 근거 대조 및 Critic을 통과해야 복구 성공  
두 번째도 실패하거나 예산이 소진되면 시장 코스 이용 불가  검증된 배편과 요금만 유지  
같은 시간 초과를 FT-02로 재분류해 세 번째 호출하지 않음  
원천 인증 오류는 재시도하지 않고 설정 확인 알림  
CI에서는 외부 LLM 모의 응답으로 재현하고 실제 연결 성공 여부와 구분

### FT-02 에이전트 실행 중 예외

Executor와 Planner 및 Critic 실행 래퍼가 내부 예외를 감지하고 AGENT_EXCEPTION 기록  
Recovery는 불완전 출력을 버리고 검증된 이전 입력으로 실패한 단계만 한 번 재실행  
에이전트 내부 DB 오류는 FT-03  외부 LLM 시간 초과는 FT-01로 처리  
재실행 결과는 형식과 서버 검증 및 Critic을 거쳐야 사용자에게 반환  
Critic이 실패해도 검증을 건너뛰지 않고 Critic 단계 재실행 후 종료  
반복 예외는 배편 조회 단계이면 요청 실패  시장 단계이면 배편 유지와 코스 실패

### FT-03 배편과 시장 조회 또는 갱신 저장 중 DB 연결 오류

연결 예외와 연결 종료 및 3초 조회 제한 초과를 감지하고 DB_UNAVAILABLE 기록  
정상 조회 0건을 DB 고장으로 처리하지 않음  
실패 연결을 버리고 미완료 트랜잭션을 롤백한 뒤 1초 후 새 연결로 한 번 재시도  
SELECT 1 확인뿐 아니라 원래 요청에 필요한 레코드 조회까지 성공해야 복구  
갱신 저장은 refresh_job_id와 자료 개정 번호를 영속 저장된 고유 키로 사용해 중복 방지  
커밋됐지만 응답만 사라졌으면 같은 키의 저장 결과를 확인하고 중복 생성하지 않음  
재실패하면 배편 조회는 503  시장 조회는 배편 유지와 코스 실패  갱신은 이전 활성 버전 유지  
검증되지 않은 메모리 스냅샷으로 DB 실패를 정상 처리하지 않음

시험에서 DB 컨테이너를 의도적으로 중지한 경우 readiness 검사만으로 자동 재기동한다고 가정하지 않음  
계속 중지된 DB는 제한 재접속 후 안전 종료와 알림  담당자가 재가동하면 원래 조회로 확인  
사람이 재가동한 사례는 수동 복구로 기록하고 자동 복구 성공에 포함하지 않음  
일시 연결 단절이 새 연결로 회복되는 경우와 지속 중지되는 경우를 나누어 시험

### FT-04 Planner 출력 수신 직후 형식 오류

JSON 파싱과 Pydantic(데이터 형식 검사)으로 필수 필드와 타입 및 추가 속성 검사  
필수 정보는 선택 배편 ID와 개정 번호 및 market_id와 place_ids 및 방문 순서와 source_ids  
실패하면 OUTPUT_SCHEMA_INVALID와 누락 필드 기록  
수정 예산이 남았으면 Recovery가 오류 목록과 허용 후보 및 서버 계산값을 넣어 Planner에 한 번 수정 요청  
수정 뒤 같은 형식 검사와 Critic을 다시 통과하면 복구 성공  
반복 오류나 이미 사용한 수정 예산이면 COURSE_INVALID  배편 유지와 코스 실패  
미검증 결과나 임의 기본 코스를 노출하지 않음

### 품질 반려와 자료 갱신 오류

Critic은 미등록 장소와 시장 연계 불일치 및 출처 누락과 서버 계산값 차이를 감지  
형식 오류와 같은 Planner 수정 예산이 남았을 때만 한 번 수정하고 다시 검증  
가격이나 운영시간의 원천 누락은 UNKNOWN으로 표시하며 모델에 사실을 채우라고 요구하지 않음

자료 갱신은 허용된 API 또는 파일로 수행하고 새 버전 형식과 적용일 및 권한 검사 뒤 저장  
실제 외부 자료 연결에서 시간 초과가 나면 한 번 재요청하고 실패 시 새 버전을 활성화하지 않음  
유효한 이전 버전은 출처와 적용일 및 마지막 성공 확인 시각을 표시하며 계속 제공  
이전 버전도 만료나 권한 미확인이면 해당 배편 선택 차단  
갱신 실패와 이전 자료 제공은 원천 정상화와 구분해 기록  
외부 자료 연결 장애는 추가 시험이며 FT-01 필수 시험은 외부 LLM 시간 초과로 통일

## 10 최종 상태와 로그 및 알림

| 최종 상태 | 사용자 표시 | 복구 집계 |
|---|---|---|
| SUCCESS | 검증된 배편과 시장 코스 | 장애 후 전체 목표 기능을 검증까지 통과하면 자동 복구 성공 |
| PARTIAL | 유효한 배편과 요금  코스는 이용 불가 | 전체 코스 복구 성공으로 세지 않음 |
| NEEDS_CONFIRMATION | 자료와 가격 및 운영정보 확인 필요 | 미확인을 정상 통과로 세지 않음 |
| FAILED | 요청 불가 이유와 문의용 trace_id | 미복구 |

stdout과 지속 보관되는 구조화 로그에 기록해 DB 중단 중에도 증거 보존  
trace_id와 incident_id  단계와 오류 코드 및 시도 횟수  복구 동작과 자료 개정 번호  
주입과 감지 및 복구 시작과 검증 완료 시각  최종 상태와 수동 개입 여부  
모델과 스키마 버전 및 거부 이유  커밋 SHA와 실행 ID 및 로그 링크  
키와 비밀번호 및 사용자 입력 원문은 제외  
DB 복구 뒤 후속 요청과 이전 장애 번호를 연결하고 실제 기록 실패를 숨기지 않음

재시도 소진과 자료 권한 오류 및 유효한 운항표 부재는 담당자 수동 개입 알림 대상  
데이터 오류는 데이터 담당  DB 오류는 서버 담당  에이전트와 배포 오류는 통합 담당  
운영 알림은 DB에 의존하지 않는 비동기 메일 작업으로 전송하고 전송 실패는 한 번 재시도 후 로그 보관  
메일 실패가 사용자 요청을 다시 실행하지 않도록 분리  
GitHub Actions는 파이프라인 결과와 실패 이메일을 담당하고 실시간 운영 감시를 대신하지 않음  
담당자와 백업 연락처 및 알림 확인 방식  [팀 입력]  
지연 경보와 자동 상향 전달은 필수 완성 후 검토하고 현재는 담당자가 로그와 메일로 수동 확인

## 11 재현 시험과 측정

시험용 Compose와 고정 자료 및 LLM mock(모의 응답)으로 먼저 정상 배편과 코스 응답 확인  
한 번에 장애 하나만 주입하고 각 필수 FT를 최소 3회 반복  
복구 경로와 지속 실패 경로를 구분하며 가능하면 경로별 3회씩 반복  
각 실행은 새 incident_id 사용  같은 장애의 내부 재시도는 같은 incident_id 유지  
장애 종류가 다르거나 여러 단계 장애가 겹치는 시험은 별도 복합 사례로 분류

시험 후 주입 설정을 끄고 같은 입력으로 정상 복귀 확인

자동 복구율  사람이 개입하지 않고 원래 목표 기능 검증을 통과한 장애 건수 ÷ 전체 필수 장애 시험 건수 × 100

유효 이전 자료 제공과 수동 복구 및 일부 기능 유지 건은 별도 집계  
미복구 종료시간과 미탐지 및 관측 종료 건도 공개  미측정 값은 미실행 또는 N/A

| trace_id와 incident_id 및 로그 링크 | [입력] |

| 평균 복구시간과 실패 원인 | [미측정] |

## 12 CI/CD와 EC2 배포

GitHub Actions(코드 검사 자동화) → 단위 및 통합과 FT 시험 → 이미지 빌드 → EC2 Compose 배포 → 준비 상태 및 핵심 요청 확인 → 기록과 이메일  
PR과 커밋의 검사는 외부 키 없이 고정 자료와 LLM mock으로 실행  
실제 LLM 연결 확인은 비밀 값을 가진 별도 수동 실행에서 수행하고 모의 시험과 구분  
필수 시험 실패는 배포 차단  실패를 무시하는 설정으로 통과시키지 않음  
외부 기여 PR에 운영 시크릿을 전달하지 않고 신뢰된 main 변경분의 검사 성공 뒤 배포  
Kubernetes는 사용하지 않음  
DB 자료는 지속 볼륨 또는 합의한 외부 DB에 보관하고 임시 컨테이너 파일에만 저장하지 않음  
DB 상태 확인과 실행 준비 순서 설정  healthcheck는 자동 재시작 보장이 아님  
배포 후 준비 상태와 배편 조회 및 시장 코스 핵심 요청 확인  
실패하면 해당 배포를 실패로 기록하고 담당자에게 알린 뒤 이전 검증 이미지로 수동 복귀  
자동 롤백과 추가 운영 기능은 필수 완성 후 선택

배포 차단 증명은 격리된 시험 실행에서 의도적으로 assertion(기대 결과 검사)을 실패시켜 수행  
시험 실패와 배포 단계 미실행 및 EC2의 배포 커밋 불변과 알림 수신을 함께 기록  
그 뒤 정상화한 성공 실행을 따로 남김  
예상 장애 처리 시험이 통과한 것과 CI 자체를 실패시키는 차단 시험을 구분

| 배포와 CI 실제 기록 | 내용 |
|---|---|
| 커밋 SHA와 실행 ID 및 이미지 식별자 | [입력] |
| 테스트 자료와 검사 범위 및 커버리지 측정 | [입력] |
| 실패 차단 실행과 deploy 미실행 증거 | [입력] |
| EC2 배포 커밋과 상태 확인 결과 | [입력] |
| 실패 알림 수신과 로그 링크 | [입력] |
| 정상화와 수동 복귀 결과 | [입력] |
